# 字节 Agent 开发（抖音）一面 · 参考答案

面经来源是小红书一面回忆，大约 60 分钟。开场简单自我介绍，之后全程沿着项目往下追。问题顺序和原话不完全一致，连续追问被拆开了。后半段会从纯 Agent 设计转到 RAG，再穿插 Agent 服务化，很少问传统八股。

下面用**同一套架构**把问题串起来，方便你按项目真实名词替换后直接讲。组件职责、数字和取舍是一套能扛住连续追问的参考实现，不是要求你声称自己线上就是这些参数。讲的时候先给结论，再补「为什么这样，坏了怎么办」。

## 0. 先统一项目设定

**项目**：内部业务 Copilot。用户用一句话做两类事：

1. 问内部知识：制度、接口文档、排障手册。
2. 做受控操作：查订单 / 查指标、建工单。改配置这类有副作用的动作，必须人工确认后才执行。

**为什么要做成多 Agent**：工具和文档域一多，单 Agent 会同时出现三件事——工具选错、上下文被无关历史撑爆、权限边界守不住。纯 RAG 又只能答单跳事实，覆盖不了「先查文档再查数再决定要不要建工单」。

**角色分工（全文都用这些名字）**：

| 角色 | 是什么 | 有没有自己的 loop |
| --- | --- | --- |
| Gateway | FastAPI 入口：鉴权、限流、SSE、取消 | 无 |
| Orchestrator | 入口也是出口。做意图、复杂度、路由、汇总 | 有，但步数很少 |
| Planner | 只对复杂请求出 DAG | 无独立工具 loop，一次或少数几次规划 |
| Knowledge / Data / Action Agent | 按职责执行的 Executor | 有，各自 ReAct |
| Verifier | 高风险或低置信时做结果校验 | 无工具，只做判定 |
| Skill | 挂在某个 Agent 上的能力包：说明、工具白名单、参数 schema、少量示例 | 无 |

**一条请求的默认链路**：

```text
用户 Query
  → Gateway（鉴权、限流、建 run_id、打开 SSE）
  → Orchestrator（读 Session 摘要，做意图 + 复杂度）
      ├─ 简单、单意图、无依赖：直接进对应 Executor，走短 ReAct
      └─ 复杂或多意图：Planner 出 DAG → 调度器按依赖串行/并行调 Executor
  → 需要时 Verifier 看「结论是否被工具结果支撑」
  → Orchestrator 汇总，经 SSE 把最终答复推给用户
  → 全程只把结构化结果写回 Session，不把子 Agent 原文塞回去
```

Session 热状态在 Redis，完整审计在 MySQL，大块工具输出在对象存储，消息里只留指针。

## 一、项目与执行链路

### 1. 先介绍一下你做的这个 Agent 项目，主要解决什么问题？

我们做的是内部业务 Copilot，服务产品、运营和研发同学。他们原来要在文档站、指标平台、工单系统之间来回切，而且很多问题不是一跳能答完的，比如「这个错误码什么意思，过去一天影响了多少单，要不要建工单」。

系统要同时满足三件事：

- 知识问题要有出处，不能凭模型记忆编内部制度。
- 多步任务要能拆开做，步骤之间的结果要能传递。
- 有副作用的操作必须有权限和人工确认，模型不能直接打到生产接口。

所以主体是一个编排 Agent 加三个执行 Agent（知识、数据、动作），工具按 Skill 挂到对应 Agent 上，而不是把所有工具塞进一个大 prompt。

### 2. 用户输入一个 Query 以后，整个系统的执行链路是什么？

1. Gateway 校验登录态，做用户级限流，生成 `run_id`，把用户消息追加到 Session，然后把这条 SSE 连接挂上。
2. Orchestrator 只读「最近几轮摘要 + 当前问题」，先做两分类：意图属于知识、数据、动作还是混合；复杂度是单跳还是多跳。
3. 单跳走短路：直接把任务信封交给一个 Executor，Executor 内部最多几步 ReAct。
4. 多跳或一个 Query 里有多件事：Planner 产出 DAG。每个节点有 `goal`、`agent`、`depends_on`、`acceptance`。调度器按依赖执行，无依赖的节点并行。
5. Executor 调工具。工具结果先做 schema 校验和截断，大结果落对象存储，上下文里只留摘要和 `artifact_id`。
6. 知识类答案要带引用；动作类在真正执行前过权限，高风险工具还会中断等用户确认。
7. 低置信、数字对不上、或高风险动作完成后，过一次 Verifier。
8. Orchestrator 用各节点的结构化输出写最终答复，SSE 推 `done`。Session 里更新的是摘要和产物指针，不是全部思维链。

### 3. 用户 Query 进来以后，最先进入哪个 Agent？

最先进入 Orchestrator，不直接进某个业务 Agent，也不先走 Planner。

它要先看 Session，处理指代（「再查一下刚才那个错误码」），并判断这次该短路还是该规划。如果一进来就进 Planner，简单问题会多一次大模型调用；如果一进来就进某个专家 Agent，混合问题又没人拆。

Orchestrator 自己几乎不调业务工具，避免它又变成一个万能 Agent。

### 4. 最后又是哪个 Agent 负责把结果返回给用户？

还是 Orchestrator 负责对用户说话。Executor 的输出是给编排层的结构化结果，默认不直接暴露给用户。

这样有三个好处：口径统一（引用格式、失败说明、下一步建议）；用户看不到内部角色之间的原始对话；某个 Executor 失败时，由 Orchestrator 决定是部分回答、重规划，还是向用户提问。

Verifier 不负责措辞，它只返回通过、不通过、以及缺了什么证据。

### 5. 中间如果涉及多个 Agent，是怎么决定应该路由到哪个 Agent 的？

分两层。

第一层是 Orchestrator 的意图路由，决定进哪个 Executor，或者要不要先规划。每个 Executor 有一张很短的 Agent Card：名字、擅长什么、不该接什么、可用 Skill 列表。路由只看 Card，不看对方的完整 prompt 和历史。

第二层在 Planner 的 DAG 里。规划结果的每个节点显式写 `agent` 字段，调度器按这个字段派发，节点执行中途不再自由跳到别的 Agent。需要别的能力时，把结果交回 Orchestrator，由它决定是否新增节点。

路由输出是约束过的 JSON：`agent`、`confidence`、`reason`。置信度低于阈值就澄清，或者降级到 Knowledge Agent 做「只读回答」，而不是猜一个会写数据的 Action Agent。

### 6. 这个路由是规则做的，还是让大模型自己判断？

是规则优先，模型兜底。

规则负责高确定信号：工单号、错误码、明确的指标名、用户点了某个快捷指令。这些命中就直接路由，省一次模型调用，也更稳。

规则没有命中，再用模型在 Agent Card 上做选择，输出必须符合 schema。模型路由会记录线上分歧样本，定期把稳定模式收成规则。

完全规则覆盖不了口语和多意图；完全模型路由又会在明显场景上浪费延迟，而且不好解释。所以两条都留，但规则能决定的，模型不能改写。

### 7. 如果用户一个 Query 里面同时包含多个任务，你们是怎么拆分的？

由 Planner 拆，不在路由阶段硬切。

例如：「查一下 E1003 的含义，再看昨天的订单量，超阈值就建工单。」Planner 产出三个节点：

1. Knowledge Agent：解释 E1003，无依赖。
2. Data Agent：查昨天订单量，无依赖，可与 1 并行。
3. Action Agent：依赖 1 和 2 的结果，并且只有指标超阈值才执行；建工单前还要用户确认。

拆分约束写在 Planner 的 prompt 里：一个节点只交给一个 Agent；节点之间只通过输入输出字段依赖；不允许一个节点里再塞第二个目标。拆得过细（每句话一个节点）会增加调度开销，所以同时限制最大节点数，超出就先做前几个并告诉用户其余下轮再做。

### 8. 任务拆分以后是串行执行还是并行执行？

看 DAG，不预设全都串行或全都并行。

没有 `depends_on` 的节点并行，用 `asyncio.gather`，每个分支有自己的超时。有依赖的等上游的结构化结果到了再开始。

并行还有三道限制：

- 同一 Session 的写操作不并行，避免两个人工确认或两次写打乱状态。
- 全局和单用户都有并发上限，防止一个 Query 把工具配额打满。
- 任一分支失败，不连带取消已经成功且无副作用的分支；有副作用的分支按自己的补偿策略处理。最终由 Orchestrator 汇总「完成了什么、哪一步失败」。

### 9. Plan Agent 和 Execute Agent 分别负责什么？

Planner 只负责「要做哪些步、谁做、依赖是什么、做到什么算过」。它不查文档、不打业务接口。输入是用户目标、Session 摘要、Agent Card。输出是 DAG。

Execute Agent 负责在自己的工具集合里把一个节点做完。它看到的是这个节点的目标、上游给的字段、验收条件，然后再走自己的短 ReAct：选工具、看观察、决定继续还是交出结果。

两者分开，是为了让规划用更强的模型、执行用更便宜的模型，也避免执行过程中的工具原文污染规划上下文。

### 10. 是不是所有任务都会先经过 Plan Agent？

不会。Orchestrator 里有一个复杂度门闩，简单任务绕过 Planner。

满足下面几条就短路到单个 Executor：

- 规则或路由只命中一个意图。
- 不需要把上一步的产物交给另一个 Agent。
- 预估工具调用不超过 2 次。
- 不是高风险写操作的组合动作。

只有多意图、多跳、或者第一次执行失败需要改计划时，才调用 Planner。失败后的重规划是增量的：把失败节点和错误类型交回去，让它改后续节点，而不是从零再写一份计划。

### 11. 如果只是一个非常简单的任务，还重新生成完整 Plan，会不会反而降低效率？

会。简单问答再走一遍 Planner，至少多一次模型往返，首字延迟经常多出一两秒，也多一份跑偏的机会。

所以简单任务不生成计划。复杂度门闩用规则就能挡掉大部分「查一个错误码、查一个指标」的请求。门闩判断错了也有退路：Executor 发现目标超出自己的 Skill，就交回 Orchestrator，再升级到 Planner，而不是在错误路径上一直试。

### 12. 简单任务为什么不能直接用 ReAct 完成？

简单任务就是直接用 ReAct 完成的。ReAct 是 Executor 内部的循环：Thought → Action → Observation，直到节点完成或步数用尽。

我们不用 ReAct 覆盖所有请求，是因为 ReAct 是边想边做，没有全局依赖图。遇到「两件事可并行，第三件依赖前两件，而且第三件会写数据」时，它容易串行乱试、重复调用，也很难在写之前插入确认。

所以策略是：单跳 ReAct，多跳 Plan-and-Execute，执行层内部仍是 ReAct。

### 13. Multi-Agent 和 Single-Agent 最大的区别是什么？

最大的区别是**控制边界和上下文边界是不是分开的**。

单 Agent 是一个 loop、一份上下文、一组工具、一个权限。多 Agent 是多个 loop，每份上下文只服务一个职责，交接时走结构化消息，权限按 Agent 收紧。

多 Agent 不是「把一个 prompt 拆成几段」就算。如果几个角色共享同一份无限增长的消息列表、还能随便调同一批工具，那只是单 Agent 换了个说法。

### 14. 多 Agent 相比单 Agent 的优势在哪里？

- **工具选择更稳**。每个 Executor 只挂自己的 Skill，候选工具少，选错率明显下降。
- **上下文更短**。知识检索的长文不会进入会执行写操作的 Action Agent。
- **权限能切开**。Knowledge / Data 默认只读；写操作只存在于 Action Agent，并且调用前还有策略校验。
- **可以并行**。无依赖的查文档和查数同时进行。
- **可以换模型**。规划用强模型，检索问答用便宜模型，成本和延迟更好控。
- **失败面更小**。一个 Agent 进入循环，只重试该节点，不必把整段对话扔掉。

### 15. 多 Agent 会带来哪些额外问题？

- 交接丢信息：上游没把关键字段写进信封，下游就会答非所问。
- 延迟和费用上升：每多一个角色就多一次模型调用。
- 责任不清：两个 Agent 都觉得该自己回答，或者都不回答。
- 状态一致：并行分支同时改 Session 会丢更新。
- 调试变难：要有 `run_id` 串起每个节点的输入、工具、输出，否则线上问题无法回放。
- 错误传播：上游错了，下游会很自信地在错误前提上继续做。

这些要靠结构化交接、复杂度短路、Session 写锁、节点级超时和 trace 来压住。多 Agent 是复杂度上来之后的拆分，不是默认配置。

### 16. 为什么不能用一个 Agent + 多个 Skill 来替代 Multi-Agent？

Skill 解决的是「能力怎么打包」，Agent 解决的是「谁在独立循环里、用什么上下文、拿什么权限」。一个 Agent 挂很多 Skill，在下面几种情况会不够：

- **工具 schema 太多**。几十个工具塞进同一次选择，模型更容易选错。Skill 可以按需激活一部分，但写权限和只读仍然在同一个 loop 里，模型只要选错一次就能碰到写工具。
- **上下文串味**。检索到的长文档、SQL 结果、用户确认卡片全在一份历史里，后面每一步都在为无关 token 付费，也更容易遗忘最初目标。
- **不能按职责并行**。一个 loop 即使一次发出多个 tool call，规划和权限模型仍然是同一个角色。
- **模型和提示词无法按任务换**。查知识想用便宜模型，规划想用强模型，拆成 Agent 才自然。

Skill 仍然有用，它是 Agent 里面的能力单元。我们的 Knowledge Agent 上会挂「制度检索」「接口文档检索」两个 Skill，而不是为每份文档再造一个 Agent。当需要独立上下文、独立权限或并行执行时，才升级成多个 Agent。

## 二、Skill、上下文、循环和失败

### 17. Skill 和 Agent 在你这里分别承担什么职责？

Skill 是静态能力包，没有自己的循环和状态。内容包括：何时使用、何时不要使用、工具白名单、参数 schema、一两个示例、输出字段要求。它在被选中的那一轮注入到 Agent 的提示里。

Agent 是运行时主体。它有自己的消息列表、步数上限、模型配置、停止条件和失败策略，并在循环里决定调用哪个已挂载的 Skill 工具。

一句话：Skill 描述「会做什么」，Agent 决定「现在做不做、做到哪停、失败了怎么办」。

### 18. Agent 之间有没有做上下文隔离？

有。每个 Agent 维护自己的消息列表。Orchestrator 不会把用户的完整历史复制给每一个 Executor。

Executor 本轮能看到的只有：

- 系统提示和自己的 Skill 说明。
- 这次任务信封：目标、约束、上游字段、验收标准。
- 自己在本节点里产生的工具调用和观察。

Session 里的长期信息先被压成摘要，由 Orchestrator 按需放进信封的 `context` 字段，例如当前正在讨论的错误码。子 Agent 结束后，完整思维过程留在 trace 里供排查，不回写到别人的上下文。

### 19. 如果做了上下文隔离，Agent 之间又是怎么进行通信的？

通过任务信封，由 Orchestrator / 调度器转发，Agent 之间不直接互相调用。

```json
{
  "run_id": "r_123",
  "node_id": "n2",
  "goal": "查询昨天 E1003 影响的订单量",
  "inputs": {"error_code": "E1003", "date": "2026-11-09"},
  "constraints": ["只读", "必须给出指标口径"],
  "acceptance": ["返回数值", "返回统计窗口", "返回来源"],
  "artifact_refs": []
}
```

下游返回同样结构化的 `outputs`、`status`、`citations`。调度器按 `depends_on` 把上游 `outputs` 映射成下游 `inputs`。缺少必填字段时，节点直接失败并说明缺什么，不会把一段自然语言硬塞给下一个模型猜。

### 20. Agent A 能不能直接看到 Agent B 的完整历史上下文？

不能。A 只能看到 B 声明过的输出字段，以及被显式引用的产物。

B 的工具原文、失败尝试和中间想法留在按 `run_id + node_id` 索引的 trace 里，给人排查用，不进 A 的 prompt。如果 A 真的需要某份原始证据，信封里给 `artifact_id`，A 用只读工具按需拉取，并受权限和长度限制。

### 21. Agent 之间传递的是完整对话，还是结构化的中间结果？

结构化中间结果。完整对话只存在于各自的节点 trace 里。

自然语言交接在多跳之后会变形：数字丢单位、条件被说反、失败被说成成功。结构化字段可以做 schema 校验，调度器也能判断依赖是否满足。对用户的最终答复才由 Orchestrator 写成自然语言。

### 22. 为什么不直接把所有上下文都塞给每个 Agent？

塞全量会直接带来四件事：token 费用和延迟上升；无关文档把当前目标挤出有效窗口；只读 Agent 看到写操作细节后更容易越权模仿；上游的错误推理被下游当成事实继承。

隔离之后，信息不足的表现是「缺字段」，这是可以在验收标准里发现并补交的。上下文过长的表现是「忘了目标还很自信」，更难发现。

### 23. 多 Agent 协作的时候，怎么避免上下文越来越长？

靠「分层存储 + 只回写摘要」：

- Session 对模型可见的部分是：系统说明、滚动摘要、最近 6 到 10 轮、当前 run 的节点状态。更早的原文在数据库里，需要时再检索。
- 每结束一个节点，用模板更新滚动摘要：目标、结论、关键实体、未完成项。摘要有长度上限，超了就再次压缩，并保留实体表（错误码、时间范围、工单号）不被压掉。
- 工具返回超过阈值就落对象存储，上下文只留前几百字和指针。
- 子 Agent 的过程消息不进入 Session。
- 单节点有步数和 token 预算，到点必须交出「已完成 / 阻塞原因」，不能无限追加观察。

### 24. 如果一个 Agent 执行失败，系统怎么处理？

按错误是不是可恢复来分支，而不是一律重试或一律终止。

1. 工具超时、429、5xx：对只读工具做有限次退避重试。重试耗尽，把结构化错误交回这个 Agent，让它换工具或换参数。
2. 参数不合法、权限不足、业务校验失败：不重试同样的调用。错误信息回到模型，它改参数或改计划。
3. 同一个节点连续失败，或错误表明目标本身超出该 Agent 能力：节点标记失败，Orchestrator 触发增量重规划。
4. 重规划仍失败：保留已成功的只读结果，向用户说明卡在哪一步、需要什么补充。
5. 写操作失败：用幂等键查询「到底写没写成功」，避免重试造成重复工单。已经写成功的，走补偿或人工处理，不静默再写一次。

整个 run 的状态是 `RUNNING → SUCCEEDED / PARTIAL / FAILED / CANCELLED`。部分成功也是明确状态。

### 25. 如果 Agent 一直重复调用同一个工具，怎么判断它进入死循环？

同时看三种信号，命中任一就打断：

- **相同调用**：工具名加规范化参数（排序后的 JSON）连续出现 3 次，或本节点累计 3 次。
- **状态没有变化**：对观察做哈希，连续两轮观察实质相同，说明环境没有新信息。
- **预算用尽**：单节点最大步数、最大工具次数、墙钟超时。简单节点步数更小，复杂节点更大，但都有硬上限。

打断之后不允许再用同一参数调用该工具。系统把「检测到重复调用」作为一条观察塞回模型；如果它再重复，节点失败并上交 Orchestrator。另外对 A→B→A 这种两个工具来回振荡，用最近 6 次调用的签名序列做检测。

### 26. Agent Loop 一般什么时候结束？

一个 Executor 的 loop 在这些时候结束：

- 模型给出符合节点 schema 的最终输出，并且必填字段都在。
- 步数、工具次数或时间预算到了。
- 检测到死循环。
- 出现不可恢复错误（权限、参数被策略拒绝且无法改正）。
- 用户取消，或上游 run 被标记取消。
- 高风险工具进入「等待确认」，loop 挂起，确认或拒绝后再继续。这是暂停，不是结束。

整个 run 的结束以 Orchestrator 发出最终答复或明确失败为准。某个 Executor 结束只代表节点结束。

### 27. 模型说自己「任务完成了」，系统就直接相信吗？还是会做结果校验？

不直接相信。完成要同时过格式校验和证据校验。

- 输出必须满足该节点的 JSON schema，缺字段视为未完成，退回 Agent 补，次数有限。
- 验收条件要能对上。要求「给出数值和口径」时，缺口径就不算完成。
- 知识答案里的每个事实性句子要能对到引用 chunk；对不上就要求重写或放弃该句。
- 数字必须能在工具结果里找到来源，禁止模型心算一个新数来收尾。
- 高风险动作看的是工具的成功回执，而不是模型的「我已经建好了」。

Verifier 只在低置信、校验失败或高风险时调用，避免每次都多一次模型开销。校验失败会回到原 Agent，并写明哪一条没过。

### 28. 如果模型选错工具了，你们系统怎么兜底？

在执行前拦住，而不是等副作用发生再后悔。

- 每个 Agent 只有自己的工具白名单，模型就算点名别的工具，运行时也找不到。
- 参数先过 JSON Schema 和业务规则（时间范围、枚举、只读 SQL）。不合法就把错误返回给模型，不发起真实调用。
- 工具描述里写清「不要在什么场景使用」，并配一个反例。
- 选错后的观察如果是空结果或明确的「工具不适用」，模型可以在预算内换工具。连续选错按失败节点处理。
- 写工具再加一道策略检查：用户权限、资源 ACL、是否需要确认。模型的选择只是提议，执行权在服务端。

线上把「选错工具」的 trace 回放成评测集，用来改路由、改工具描述，或者把高混淆工具拆到不同 Agent。

### 29. 工具调用超时或者返回异常以后，是直接终止还是继续让 Agent 重试？

看错误类型和工具有没有副作用。

- 只读工具的超时、连接重置、429、5xx：指数退避加重试抖动，最多 2 次。每次超时单独设置，短于用户侧的总预算。
- 写工具不因超时而盲目重试。先用幂等键查询状态：查到成功就继续往下，查到失败才允许重试一次，查不到就标记未知并交给人。
- 4xx 里的参数错误、权限错误不重试，直接作为观察返回给 Agent。
- 重试耗尽后，不把整个用户请求一刀切掉。节点失败，Orchestrator 根据剩余计划决定部分回答或改计划。

重试发生在工具适配层，模型无感知那几次 HTTP 重试。只有最终失败才进上下文，避免模型在同一次失败上再发起一轮相同调用。

### 30. 如果换一个底层大模型，你们整个 Agent 架构需要改多少？

架构不用改，改的是适配层和提示词。前提是一开始就把模型挡在统一接口后面：

- 输入是统一的消息、工具 schema、温度和最大 token。
- 输出被适配成统一的「文本增量 / 工具调用 / 结束原因」。不同厂商的 function call 格式、思考字段、特殊标记都在适配器里抹平。
- Agent 逻辑只依赖这个统一结构，不解析某个厂商的原始报文。

换模型时实际要重做的是：系统提示的措辞、工具描述的详细程度、路由置信度阈值、上下文长度预算，以及一轮回归评测（路由准确率、工具参数合法率、引用命中、端到端任务成功率）。

不需要改的是：DAG 调度、Session、权限、RAG 索引、SSE 和取消。如果某个模型工具调用很弱，就把该 Executor 换成更稳的模型，而不是改业务代码。

## 三、RAG

面试里如果只讲「进向量库，top-k 召回，再 rerank」，会被认为没做过。下面按数据进系统到生成的顺序讲。

### 31. 你这个项目里的 RAG 是怎么做的？从文档进入系统开始完整讲一下

**离线入库**

1. 接入：文档站、手册 PDF、接口 Markdown 通过同步任务增量拉取，记录 `doc_id`、来源、更新时间、ACL。
2. 解析：保留标题层级。正文、表格、代码块分开处理。页眉页脚、目录页去掉。表格转成「表名 + 列名 + 行」的文本，避免把格子切碎。
3. 切块：按标题做父块，父块再切成用于召回的子块。父子用 `parent_id` 关联。细节见下一题。
4. 索引：同一批 chunk 同时建两份索引。稀疏用 Elasticsearch 的 BM25，稠密用向量库。两边使用同一个 `chunk_id`。向量模型用支持中英和关键词的双编码器，入库和查询用同一模型、同一归一化。
5. 元数据：标题路径、来源、更新时间、ACL、是否表格，全部带上，过滤在召回阶段就能做。

**在线查询**

1. Orchestrator 确认这是知识问题，把任务交给 Knowledge Agent。
2. 查询侧先做受限改写（下一题），同时保留用户原句。
3. 混合召回：原句和改写句各走 BM25 和向量，各取 50，用 RRF 融合（常数 k 取 60），并按 ACL、时间做过滤。
4. 融合后的前 20 条交给交叉编码器做 rerank，取得分最高的 5 条。
5. 生成时不用过短的子块，而是取对应父块，并按 `doc_id + parent_id` 去重，避免同一段重复占窗口。
6. 提示词要求只根据给定材料回答，并在句后标引用编号。材料分数低于阈值就明确说没查到，不让模型用参数知识补内部制度。
7. 引用校验：答案中的引用必须来自这次检索结果。校验失败则重写一次或退回「依据不足」。

Knowledge Agent 的工具就是这套检索，不是让模型自己拼查询 DSL。

### 32. 原始文档是怎么切 Chunk 的？Chunk Size 和 overlap 多少？怎么确定？

按结构切，不按固定字数一刀切。

- 先按标题把文档切成父块。一个父块是完整小节，上限大约 1200 到 1500 token，超长小节再按段落切开。
- 父块内部切子块用于召回。子块目标大小 **512 token**，**overlap 64 token**（大约 12%）。重叠是为了保住跨段落边界的那句话，不是为了越大越好。
- 代码块和表格不再从中间切开，即使略超 512 也整段作为一个子块；过大的表按行组切，并在每组重复表头。

这组数不是拍脑袋定的。我们拿大约 80 到 100 条真实问答做离线扫描，子块尺寸试 256 / 512 / 1024，重叠试 0 / 64 / 128，看两组指标：

- 召回：标注依据有没有出现在 rerank 后的 top-5 里。
- 回答：引用是否支持结论，有没有明显截断导致的半句话。

256 召回碎、指代丢失；1024 召回里噪声多，rerank 也更贵。512 + 64 在这批评测上最好。上线后如果某类文档（比如超长排障步骤）效果差，只调那类文档的切分模板，不全局改。

### 33. 用户 Query 进来以后，在检索之前有没有做 Query Rewrite？

有，但改写是受限的，而且原句一定参与检索。改写只做三件事：

- **指代消解**：结合 Session 里的实体表，把「它」「刚才那个」补成错误码或文档名。
- **多意图拆开**：一个问题里的两个知识子问题拆成两次检索，避免一个向量同时靠近两个主题。
- **补同义口径**：内部黑话和文档用词不一致时，补一个更接近文档表述的说法，例如口语里的「单量」对指标全称。

不做的事：不补充用户没说的原因，不把问题改成更「好答」的另一题，不生成假设性答案再去检索。改写用一次便宜模型调用，输出 JSON：`resolved_query`、`sub_queries`。失败就退回原句，检索不阻塞。

### 34. Query Rewrite 如果把用户原始意图改错了怎么办？

原句和改写句一起召回，改写没有覆盖原句的权力。

另外有三道防护：

- 改写结果和原句做字面重合检查。实体（错误码、专有名词、数字、时间）必须保留，丢了就废弃这次改写。
- 融合排序时原句命中的 chunk 有保底名额，避免改写句把正确文档全部挤掉。
- trace 里同时留下原句和改写句。线上抽样看「改写后召回变差」的案例，用来收紧改写提示词。

用户侧不展示改写过程，但答案仍以原问题为回答目标。材料只支持改写后的问题、不支持原问题时，按没查到处理，并告诉用户目前能确认的范围。

### 35. 为什么检索要用 BM25 + Dense，只用 Dense 不行吗？

内部语料里，很多关键查询是精确匹配：错误码 `E1003`、接口名、配置项、人名、指标 ID。稠密向量擅长语义相近，对这种稀疏、少见、一个字符就不同的词不稳，有时近邻是解释类似但代号不同的另一段。

BM25 正好补上精确词命中。反过来，用户用口语问、文档用书面说法时，BM25 会漏，稠密检索能补上。

所以两边各召回一批，用 RRF 融合，再交给 rerank 做精排。RRF 不依赖两边分数的绝对值，避免 BM25 和向量分数量纲不同、硬加权很难调。

只用稠密在「语义问答」演示集上往往够用，在带大量代号和专有名词的内部文档上，混合检索的 top-5 依据命中率更高。代价是多一路索引和查询，要在同一 `chunk_id` 上对齐，并控制两路超时，某一路超时就用另一路降级，不让检索整体失败。

## 四、Agent 服务化

面经后半段重新从 1 编号，问的都是线上服务，不是算法概念。

### 1. Agent 的流式响应是怎么实现的，为什么用 SSE？

Gateway 对聊天接口返回 `Content-Type: text/event-stream`。Agent 每产生一小段就往连接上写一个事件，前端按事件类型渲染。

事件大致是：

```text
id: 17
event: token
data: {"run_id":"r_123","text":"昨天"}

id: 18
event: tool_start
data: {"name":"query_metric","args":{"code":"E1003"}}

id: 19
event: tool_end
data: {"name":"query_metric","summary":"订单量 128"}

id: 20
event: done
data: {"status":"SUCCEEDED"}
```

模型侧使用流式接口，token 到了就转发，不等整段生成完。工具开始和结束也推给前端，否则长任务期间页面会像卡住。每 15 秒写一条注释心跳 `: ping\n\n`，避免网关或浏览器把空闲连接断开。

用 SSE 是因为这条链路本质是服务端单向推给浏览器：实现在普通 HTTP 上，穿透公司代理比 WebSocket 省事，断线可以用 `Last-Event-ID` 补事件。用户取消、发新消息走单独的 POST，不需要一条双向长连接。WebSocket 适合服务端和客户端都要高频互发的场景，这里用不上。

### 2. 用户主动停止生成或者网络断开以后，后端怎么终止当前 Agent 任务？

停止是协作式取消，加上状态落库，不是只把 HTTP 连接掐掉。

- 用户点停止：前端 `POST /runs/{run_id}/cancel`。Gateway 在 Redis 里把 run 状态写成 `CANCELLED`，并 `cancel()` 对应的 asyncio 任务。
- 网络断开：SSE 的发送循环捕获连接断开，走同一条取消路径。只断连接、不改状态的话，后端还会继续调工具烧钱。
- 取消点设在循环的边界：每次模型请求前、每个工具调用前、每个流式分片之间检查标志。工具适配器把取消传进去，能中断的 HTTP 请求用 `httpx` 的取消；已经发出的写请求不硬掐，用幂等键确认结果后再决定要不要补偿。
- `finally` 里释放 Session 锁、关掉模型流、把已产生的部分文本标成「已停止」。再次进入这个 Session 时，用户能看到停在哪里。

任务对象放在本进程的 `run_id → Task` 映射里。多实例部署时，取消请求可能打到另一台机器，所以 Redis 标志是权威状态，每台机器上的循环都认这面旗。

### 3. Python 里多个 Tool 同时调用时，怎么做异步并发？

工具都是 I/O（HTTP、检索），用 `asyncio.gather` 并发，并加信号量限制同时在途的数量。

```python
sem = asyncio.Semaphore(5)

async def run_one(call):
    async with sem:
        return await tool_registry.invoke(call.name, call.args)

results = await asyncio.gather(
    *(run_one(c) for c in tool_calls),
    return_exceptions=True,
)
```

`return_exceptions=True` 让一个工具失败不会把同一批里其他工具的结果丢掉。返回给模型时按原顺序组装，每条标明成功或失败。

CPU 密集的活（大文档解析）不放在事件循环里，用 `asyncio.to_thread` 或单独的进程池。写工具即使模型一次返回了多个，服务端也改成串行，并逐个做权限和幂等检查。

### 4. FastAPI 中如果异步接口里出现阻塞操作，会有什么问题？

`async def` 接口跑在事件循环上。里面如果出现 `time.sleep`、同步的 `requests`、同步数据库驱动或大段 CPU 计算，会把整个循环堵住。

表现是：这个 worker 上别的请求进不来，包括健康检查；已经挂着的 SSE 心跳发不出去，代理认为连接死亡；一个慢工具会把同一进程里所有用户的延迟抬高。Agent 场景里工具时延本来就长，阻塞一次的影响面是整进程，不是单请求。

处理原则：能用异步客户端就用异步客户端（`httpx.AsyncClient`、异步 Redis、异步 DB）。必须用同步库时，显式丢到线程池，并限制线程池大小，避免阻塞从事件循环转移到无限线程。上线前用压测看「一个故意睡眠的请求会不会拖垮并行的短请求」，会拖垮就说明循环被堵住了。

### 5. Agent 任务执行时间比较长时，后端一般怎么处理这种长连接请求？

分两类。

交互式对话，用户在等字：保持 SSE。要做的是心跳、代理读超时大于心跳间隔、模型与工具各自的超时、以及总 run 超时。连接只负责推事件，不在这条连接里占着数据库事务。

超过几十秒、或者用户不必盯着的任务（批量分析、长报告）：接口立刻返回 `202` 和 `run_id`，真正的循环进任务队列，由 worker 执行。前端用 `run_id` 订阅进度 SSE，或轮询状态。worker 每完成一个节点就把检查点写入数据库，进程重启后从最后一个成功节点继续，而不是整单重跑。

无论哪种，网关超时和 Agent 超时分开配置。网关不能等模型默认的无限等待。队列要有长度上限，堆满了就拒绝新任务，而不是无限收。

### 6. Agent 的 Session 和对话状态一般存在哪里？

分三层，不放在进程内存里当权威数据。

- **Redis**：当前 Session 的热状态。滚动摘要、最近几轮、实体表、run 状态、分布式锁。设置 TTL，例如空闲 24 小时过期。多实例都能读。
- **MySQL**：全量消息、节点输入输出、工具审计、最终状态。用来回放和追责，不在每次模型调用时整表读取。
- **对象存储**：超长工具结果、原始检索片段、生成的文件。消息和 Redis 里只存 `artifact_id` 和摘要。

进程内存里可以有短生命周期的 `run_id → Task` 映射，丢了也能靠 Redis 里的取消标志和 MySQL 里的检查点恢复。Session 的键是 `session_id`，run 的键是 `run_id`，一次会话可以有多次 run。

### 7. 多个请求同时操作同一个 Session 时，怎么保证状态不会冲突？

一个 Session 同一时刻只允许一个 run 写。用 Redis 锁：`SET lock:{session_id} {run_id} NX PX 30000`，执行过程中续期。锁里的值必须是自己的 `run_id`，释放时用 Lua 比较后再删，避免删掉别人的锁。

第二个请求拿到锁失败时，如果前一个 run 还在生成，就返回「上一条还在进行」，前端可以取消旧的再发新的。取消成功、锁释放之后，新请求才写入。

消息是追加写，带递增序号。检查点用版本号做乐观锁，旧版本写不进去。工具副作用使用 `session_id + node_id + tool_name + 参数哈希` 作为幂等键，锁过期后重入也不会重复建单。

不依赖「单进程全局变量加锁」，因为线上至少是多 worker、多实例。

### 8. Agent 调用外部模型或者第三方 API 超时、失败时，后端怎么做容错？

把外部依赖当成会失败的部件，而不是当成函数调用。

- **超时预算**：连接超时和读超时分开。单次工具超时加上重试，必须小于这个节点的预算，节点预算小于整次 run 的预算。
- **重试**：只对幂等请求。指数退避加抖动，最多 2 次，尊重 `Retry-After`。
- **熔断**：按依赖统计错误率，连续失败后熔断一段时间，直接返回「依赖不可用」，避免把线程和连接池打光。
- **舱壁**：模型和每个关键第三方用各自的连接池与并发上限，检索挂了不影响还能查指标。
- **降级**：主模型超时切到备用模型；混合检索一路超时就用另一路；都失败就向用户明确报依赖失败，不返回猜测答案。
- **错误进上下文的形式**：给模型的是类型、可重试与否、简短原因，不给堆栈和内部地址。

这些策略放在客户端适配层，Agent 循环只看见统一的工具结果对象。

### 9. Agent 服务怎么做接口限流和并发控制？

分层做，每一层防的事情不一样。

- **入口限流**：按用户和按应用做令牌桶，挡突发聊天请求。触发时返回 429，带 `Retry-After`。
- **run 并发**：全局同时跑的 Agent 数量有上限，按用户也有上限。超过的请求排队，队列满则拒绝。防止一个脚本打满模型配额。
- **模型配额**：对模型服务单独限流，和业务 QPS 分开。规划模型与执行模型的额度也分开，避免规划把执行打光。
- **工具配额**：检索、指标、工单各自的并发和 QPS。一个 Agent 的 `gather` 还要再套信号量。
- **超时即释放**：所有名额在 `finally` 里归还，取消的 run 也归还。

限流状态放 Redis，保证多实例一致。优先级上，在线对话高于离线批任务，批任务在配额紧张时先被推迟。

### 10. 如果 Agent 需要执行高风险工具操作，后端怎么做鉴权和权限控制？

模型没有权限，用户才有。调用链路上身份从 Gateway 的登录态一路传到工具层，工具层不接受模型在参数里自填的用户 ID。

每个工具在注册表里声明风险等级和所需权限：

- 低风险只读：Knowledge、Data 的 Agent 可调用，再按数据 ACL 过滤行级或文档级权限。
- 高风险写操作：只有 Action Agent 的白名单里有它。调用前做一次策略判断，检查这个人有没有该资源的写权限。
- 需要确认的操作：策略通过后先不执行。SSE 推一个确认卡片，内容包括工具名、关键参数、影响范围。用户确认会生成一个短时、一次性的批准令牌，令牌和这次 `run_id`、工具名、参数哈希绑定。工具层校验令牌后才真正调用。用户改了参数就要重新确认。

服务端使用最小权限的下游凭证，不把万能密钥放进提示词或工具参数。每次真实调用写审计日志：谁、在哪个 run、批准了什么、下游回执是什么。日志不能被 Agent 改写。

这样即使用户话术要求「跳过确认直接改」，模型也只是又一次提出调用，执行器仍然会停在确认这一步。

## 五、60 分钟里建议的讲法

面试官会顺着你刚说的名词往下钻。开场用第 1 到第 4 题把链路讲完，后面大多数题都是这条链路的展开。

可以主动埋三个容易被追问、而且你准备好了的点：

1. **简单问题绕过 Planner，直接 ReAct。** 后面会问效率、为什么还要多 Agent。
2. **Agent 之间只传结构化信封，上下文隔离。** 后面会问通信、上下文膨胀、失败处理。
3. **检索是父子切块加 BM25/向量混合，原句和改写一起召回。** 这是 RAG 段落里最容易被追深的三处。

数字尽量固定，前后不要矛盾：子块 512 token、重叠 64；两路各召回 50，RRF 后 rerank 20 选 5；同一工具相同参数连续 3 次算循环；只读超时最多重试 2 次；SSE 心跳 15 秒；Session 写锁按 `session_id` 放在 Redis。

如果被问到「你线上是不是就是这个数」，没有离线扫描就不要说已经扫过 100 条。改成：「初值用 512 和 64，上线后按召回命中和截断案例再调。」评测方法可以讲，没做过的实验不要讲成做过。
