开源 RAG 框架全景调研报告

RAG（Retrieval-Augmented Generation，检索增强生成）是大模型落地的核心架构：把私有知识"检索"出来再"喂"给 LLM 生成答案。本报告梳理 2026 年 GitHub 上主流的开源 RAG 框架与配套生态，按「原理 → 全景 → 数据 → 详解 → 选型与学习路径」组织，供系统学习与选型参考。

📅 调研时间：2026-10 ⭐ 星标为约数（2026 年初口径，† 为估计值），以仓库实时为准 🔗 所有项目均附 GitHub 地址

RAG 是什么？为什么需要它

LLM 的训练数据有截止日期、看不到你的私有文档、还会"一本正经地胡说八道"（幻觉）。RAG 的思路：先从你的知识库里检索相关内容，再让 LLM 基于检索结果作答——相当于开卷考试。它比微调更便宜、知识可随时更新、答案可溯源到原文。

解决 · 知识时效
知识库即改即生效
更新文档重新索引即可，无需重训模型
解决 · 私有数据
企业文档 / 个人笔记可问答
数据不出本地，检索后才进模型上下文
解决 · 幻觉
答案带引用、可溯源
生成被约束在检索到的证据上（grounding）

2026 年的四个关键认知

趋势 · 检索基线
混合检索 + 重排 = 生产标配
向量（语义）+ BM25（关键词）并行召回，再用 cross-encoder 精排——被评测为"RAG 中性价比最高的升级"
趋势 · 架构演进
Agentic RAG 成为主流叙事
检索从"单步查询"变成 Agent 的规划-执行-反思循环：先想清楚查什么、要不要再查、查到的够不够
趋势 · 图谱检索
GraphRAG 补足多跳问题
微软 GraphRAG / LightRAG 用知识图谱回答"A 和 B 什么关系"这类向量检索搞不定的全局性问题
趋势 · 工程方法
评估先行（Eval-Driven）
用 RAGAS 等指标（忠实度、上下文召回率）量化每次改动，而不是"凭感觉调 prompt"

开源生态全景：六大类工具

"RAG 框架"在 GitHub 上实际是一个生态：从文档解析到评估监控，每一环都有专门的开源项目。点击卡片展开该类目的代表项目。不要试图一个框架解决所有环节——常见做法是"编排框架 + 专项工具"组合。

🧩 编排 / 开发框架

›

代码优先，提供 Pipeline 抽象，自己组装每个环节。灵活性最高。

  • LangChain≈125k⭐ · 生态最大的通用 LLM 应用框架，RAG 是其能力之一，配 LangGraph 做 Agent 编排
  • LlamaIndex≈46.5k⭐ · RAG 专精框架，数据连接器最全，索引结构最丰富
  • Haystack≈24k⭐ · deepset 出品，显式 Pipeline + 内置评估，生产级稳定
  • DSPy≈20k⭐† · 斯坦福出品，声明式编程 + 自动优化 prompt，把提示词当可训练参数

🚀 端到端平台（带 UI）

›

Docker 一键起、Web 界面操作，开箱即用的知识库问答产品。

  • Dify≈114k⭐ · 可视化工作流 + 内置 RAG 知识库的低代码 LLM 平台
  • RAGFlow≈70k⭐ · 深度文档理解的企业级 RAG 引擎，中文复杂文档强项
  • Kotaemon≈20k⭐† · Cinnamon 出品的 RAG UI，支持本地模型与 GraphRAG
  • QAnything≈13k⭐† · 网易有道出品，两阶段检索（粗排+精排）知识库问答
  • Verba≈7k⭐† · Weaviate 出品的个人 AI 助手，向 Weaviate 生态亲和
  • Cognita≈3k⭐† · TrueFoundry 出品，MLOps 风格的模块化生产 RAG

🪶 轻量 / 图谱引擎

›

单一检索策略做到极致：知识图谱检索或极简嵌入库。

  • LightRAG≈27.4k⭐ · 港大 HKUDS 出品，图 + 向量双层检索，索引开销远低于微软 GraphRAG
  • GraphRAG≈30k⭐† · 微软出品，LLM 抽取知识图谱 + 社区摘要，擅长全局性问题
  • txtai≈12k⭐† · 嵌入数据库 + RAG 工作流一体，API 极简，适合嵌入现有应用

📄 文档解析（数据摄入）

›

RAG 质量的第一道关口：把 PDF / Office / 网页转成干净的结构化文本。

  • MinerU≈45k⭐† · 上海 AI Lab（OpenDataLab）出品，PDF→Markdown/JSON，中文与扫描件表现突出
  • Docling≈40k⭐† · IBM 出品，格式支持最广（PDF/DOCX/PPTX/XLSX/HTML/EPUB），基准评测领先
  • MarkItDown≈60k⭐† · 微软出品，各类 Office 文档转 Markdown，轻量通用
  • Unstructured≈11k⭐† · 复杂版面解析老牌选手，v0.18 重做了 RAG 分块 API
  • LlamaParseLlamaIndex 官方解析 API，与 LlamaIndex 无缝集成（闭源服务）

🗄️ 向量数据库

›

存储与检索向量的专门数据库，多数框架都支持插拔替换。

  • pgvector≈15k⭐† · Postgres 扩展，业界共识的"默认起步选项"，量大再迁移
  • Milvus≈35k⭐† · 分布式架构，十亿级向量大规模场景首选
  • Qdrant≈24k⭐† · Rust 编写，高性能，元数据过滤检索强
  • Chroma≈20k⭐† · 嵌入式向量库，原型开发最简单
  • Weaviate≈14k⭐† · 混合搜索 + 模块化集成见长
  • FAISS≈40k⭐† · Meta 出品的检索算法库（无服务化），研究常用

📊 评估与观测

›

量化 RAG 效果：检索准不准、答案忠不忠实，让迭代有据可依。

  • RAGAS≈8k⭐† · 采用最广的 RAG 评估库：忠实度 / 上下文召回 / 答案相关性 + 合成测试集
  • DeepEval≈8k⭐† · pytest 风格的 LLM 单元测试，天然适合 CI/CD
  • TruLens≈2.5k⭐† · tracing + 反馈函数，定位 RAG 链路哪一环出错

核心框架深度评测

左侧选择框架查看：定位、优劣势、最小代码示例与适用判断。示例代码均基于各框架当前主流 API（2026）。

LlamaIndex

github.com/run-llama/llama_index
PythonMIT编排框架RAG 专精

定位：以"数据"为中心的 RAG 框架——从数据摄入、索引到查询的完整抽象层，被普遍认为是学习 RAG 与构建 RAG 专精项目的第一选择。

优势

  • 数据连接器最全：LlamaHub 160+ 数据源（PDF/数据库/Notion/Slack…）
  • 索引结构丰富：向量 / 树 / 知识图谱 / 递归 / 自动合并（auto-merging）
  • Workflows 事件驱动编排，高级检索（COLBERT、句子窗口）开箱可用
  • MIT 许可 + 文档教程质量高，社区以 RAG 场景为主

局限

  • 抽象层次多，概念量大（Index/Retriever/QueryEngine/Node/Postprocessor）
  • 迭代快，旧 API 弃用频繁，教程代码容易过时
  • 深度定制仍需读源码
适合：RAG 是项目核心、数据源复杂、想在代码层精细控制检索策略。学 RAG 原理的最好入口。
# pip install llama-index
from llama_index.core import VectorStoreIndex, SimpleDirectoryReader

docs = SimpleDirectoryReader("data").load_data()      # 摄入文档
index = VectorStoreIndex.from_documents(docs)              # 分块+向量化+建索引

engine = index.as_query_engine(similarity_top_k=4)          # 组装查询引擎
print(engine.query("这份文档讲了什么？"))                  # 检索+生成

LangChain

github.com/langchain-ai/langchain
Python / JSMIT编排框架生态最大

定位：星标最高的通用 LLM 应用开发框架，RAG 只是它能力版图的一块。复杂有状态应用建议搭配其兄弟项目 LangGraph（图结构 Agent 编排）。

优势

  • 生态与社区最大：模型 / 向量库 / 工具集成 800+，遇到问题几乎都有人踩过坑
  • LCEL 声明式链式组装，LangGraph 表达"检索→判断→再检索"的 Agentic 循环
  • LangSmith 提供全链路可观测（追踪/评估/监控）

局限

  • 抽象重、包拆分多（langchain-core / community / partner 包），版本迁移成本高
  • API 迭代激进，弃用警告常见，老教程大量失效
  • RAG 专精度不如 LlamaIndex
适合：RAG 要嵌入更大的 LLM 应用（Agent + 工具调用 + 多步推理），或团队想要最全的集成生态。
# pip install langchain langchain-chroma langchain-openai
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.runnables import RunnablePassthrough
from langchain_chroma import Chroma
from langchain_openai import ChatOpenAI, OpenAIEmbeddings

vectorstore = Chroma(embedding_function=OpenAIEmbeddings())
retriever = vectorstore.as_retriever(search_kwargs={"k": 4})

prompt = ChatPromptTemplate.from_template(
    "仅根据以下上下文回答：\n{context}\n\n问题：{question}")

chain = ({"context": retriever, "question": RunnablePassthrough()}
         | prompt | ChatOpenAI())          # LCEL 管道
print(chain.invoke("什么是混合检索？").content)

Haystack 2.x

github.com/deepset-ai/haystack
PythonApache-2.0编排框架生产级

定位：deepset 出品的 AI 编排框架，2.x 采用显式组件模型——每个组件输入输出强类型，Pipeline 连接关系一目了然，天然适合企业级维护与测试。

优势

  • 显式 Pipeline：组件像搭积木一样 connect，类型检查避免接线错误
  • 内置评估组件，Pipeline 可序列化为 YAML，方便版本管理与审计
  • API 稳定政策友好，欧洲企业合规场景采用多

局限

  • 社区规模小于 LangChain / LlamaIndex，中文资料少
  • 工程味重，快速原型不如 LlamaIndex 简洁
  • 前沿玩法（新检索论文复现）跟进稍慢
适合：企业生产系统、可维护性与可测试性优先、需要审计与合规的场景。
# pip install haystack-ai
from haystack import Pipeline
from haystack.components.retrievers.in_memory import InMemoryEmbeddingRetriever
from haystack.components.generators import OpenAIGenerator
from haystack.components.builders import PromptBuilder

prompt = PromptBuilder(
    "根据以下文档回答：\n{% for d in documents %}{{ d.content }}\n{% endfor %}问题：{{ question }}")

pipe = Pipeline()
pipe.add_component("retriever", InMemoryEmbeddingRetriever(document_store))
pipe.add_component("prompt", prompt)
pipe.add_component("llm", OpenAIGenerator())

pipe.connect("retriever.documents", "prompt.documents")  # 显式接线
pipe.connect("prompt", "llm")
print(pipe.run({"retriever": {"query": "什么是混合检索？"},
                  "prompt": {"question": "什么是混合检索？"}}))

Dify

github.com/langgenius/dify
Python + TSApache-2.0*低代码平台带 Web UI

定位：星标第二高的开源 LLM 平台。可视化拖拽编排工作流 + 内置 RAG 知识库，让非开发者也能搭出"上传文档 → 知识库问答机器人"。

优势

  • 知识库全图形化配置：分段策略、检索方式（向量/全文/混合）、top-k、重排模型都是下拉框
  • 100+ 模型供应商接入，团队协作 / 权限 / API 发布齐备
  • RAG 只是入口：工作流、Agent、文本生成应用同平台搞定

局限

  • 平台约束：深度定制检索逻辑要绕路（API / 插件），不如代码灵活
  • 许可含附加条款（多租户 SaaS、品牌展示限制），商用需读协议
  • Docker 全家桶部署，资源占用不小
适合：快速交付企业知识库问答、团队里有非开发成员参与、需要低代码 + 可视化运维。
# 安装（Docker Compose 一键起全栈服务）
git clone https://github.com/langgenius/dify.git
cd dify/docker
cp .env.example .env
docker compose up -d

# 浏览器打开 http://localhost/install 初始化后：
# 1. 「知识库」→ 创建 → 上传文档 → 选分段与检索策略（可开混合检索+重排）
# 2. 「工作室」→ 创建聊天助手 → 关联知识库 → 发布为 WebApp / API

RAGFlow

github.com/infiniflow/ragflow
PythonApache-2.0端到端引擎深度文档理解

定位：infiniFlow 出品的 RAG 引擎，招牌是 DeepDoc 深度文档理解——把 PDF 里的表格、图片、版面结构真正解析出来，并提供带溯源高亮的答案。

优势

  • 文档理解是同类最强档：版面分析 / 表格结构识别 / OCR，中文 PDF 表现尤其好
  • 引用溯源（grounded citation）：答案高亮原文出处，可点回原文位置
  • 模板化分块（问答 / 论文 / 法律 / 简历 / 手册）+ 多路召回 + 可配重排
  • 版本迭代活跃（v0.26+ 带 Agent 能力）

局限

  • 资源占用偏高（文档解析吃 CPU / 显存），小机器跑得吃力
  • 想改检索内核需要理解其源码结构，社区中文为主
  • 作为"引擎"边界清晰，但通用编排能力弱于 Dify
适合：中文复杂文档（扫描件 / 合同 / 报表 / 论文）知识库问答——这也是它在国内爆火（≈70k⭐）的基本盘。
# 要求：CPU ≥ 4 核 / RAM ≥ 16 GB / 磁盘 ≥ 50 GB
git clone https://github.com/infiniflow/ragflow.git
cd ragflow/docker
docker compose -f docker-compose.yml up -d

# 打开 http://localhost 即可用：
# 知识库 → 上传 PDF（自动 DeepDoc 解析：版面/表格/OCR）
# → 选分块模板 → 建聊天助手，答案自带原文引用高亮
# 检索设置可开：向量 + 全文关键词混合召回 + 重排模型

LightRAG

github.com/HKUDS/LightRAG
PythonMIT图谱检索论文出身

定位：港大数据智能实验室（HKUDS）的论文项目：用 LLM 从文档抽取实体关系建轻量知识图谱，查询时"图 + 向量"双层检索，主打低索引成本。

优势

  • 图检索回答关系型 / 多跳问题（"A 和 B 通过什么联系起来？"）
  • 索引 token 开销比微软 GraphRAG 低一个量级（查询侧 <100 token/次）
  • 查询模式可选：local（局部实体）/ global（全局主题）/ hybrid
  • 代码量小，适合读懂 GraphRAG 原理

局限

  • 学术出身，工程化（并发/运维/UI）一般
  • 有独立复现指出其论文宣称的胜率偏高（争议约 +33pp），事实型检索未必赢 Naive RAG
  • 大规模生产案例尚少
适合：研究图谱增强检索、低预算尝试 GraphRAG、关系密集型语料（人物/事件/组织）。
# pip install lightrag-hpo

               embed_model=..., llm_model_func=...)   # 可接 Ollama 本地模型

                  param=QueryParam(mode="hybrid")))  # 图+向量混合

txtai

github.com/neuml/txtai
PythonApache-2.0轻量引擎嵌入数据库

定位："一个库 = 向量检索 + 全文检索 + SQL + LLM 工作流"的紧凑型搜索栈。没有平台、没有服务化，嵌入现有 Python 应用最顺滑。

优势

  • API 极简，从建索引到检索三五行代码
  • embeddings database 原生支持混合（向量+SQL 过滤+全文）
  • 零重型依赖，适合小项目 / 边缘场景 / 教学

局限

  • 生态与集成远小于三大编排框架
  • 分布式 / 海量数据 / 高并发场景能力有限
  • 高级检索策略（重排/查询改写）要自己搭
适合：个人工具、内部小系统、给已有应用快速加一个"文档问答"功能。

按场景选型

没有"最好的框架"，只有匹配团队与场景的选择。以下是 2026 年社区的主流共识：

🎯 快速原型 / 个人学习

txtai / Kotaemon 起步最快；想顺便学代码层原理则直接上 LlamaIndex（官方 5 行代码入门教程）。本地隐私优先配 Ollama。

🏢 企业知识库（非开发团队用）

Dify（可视化编排 + 知识库，通用性最好）或 RAGFlow（文档解析深度更强）。两者都是 Docker 部署 + Web UI，RAGFlow 解析中文复杂文档的优势明显。

🇨🇳 中文复杂文档（扫描件 / 合同 / 报表）

RAGFlow 平台方案；自研路线则 MinerU / Docling 解析 + bge-m3 嵌入 + bge-reranker 重排（注意 MinerU 的 AGPL 许可）。

⚙️ 代码级生产系统

LlamaIndex（RAG 专精、迭代快）或 Haystack（显式管道、稳定 API、内置评估）；向量库 pgvector 起步 → Milvus/Qdrant 上规模；评估用 RAGAS + DeepEval 进 CI。

🤖 RAG 嵌入 Agent 应用

LangChain + LangGraph：把检索做成 Agent 可调用的工具，配合 LangSmith 观测多步检索循环。DSPy 适合想把 prompt/检索参数"自动调优"的团队。

🕸️ 关系 / 多跳问题（GraphRAG）

预算够、要全局摘要能力选 微软 GraphRAG；轻量低成本选 LightRAG（注意其评测争议）。两者也可与普通 RAG 并存路由。

推荐学习路径（约 6–8 周）

原则：先用裸代码理解原理，再用框架提效，最后上生产化与前沿架构。

第 1–2 周

裸写 Naive RAG，理解每个环节

不用任何框架：手写分块 → 调 embedding API → 余弦相似度检索 → 拼 prompt 生成。体会 chunk 大小 / 重叠 / top-k 对效果的影响。工具：sentence-transformers + FAISS/Chroma。

第 3–4 周

上手框架：LlamaIndex 为主线

跑通官方 starter，再逐步替换组件：换向量库（Chroma → pgvector）、换嵌入模型（bge-m3）、用 Docling / MinerU 解析真实 PDF 而不是 toy 数据。

第 5–6 周

生产化：混合检索 + 重排 + 评估

加 BM25 + 向量混合召回（RRF 融合）；加 重排模型（bge-reranker-v2-m3）；用 RAGAS 建立忠实度 / 上下文召回基线，每改一版跑一次评估；加元数据过滤。

第 7–8 周

进阶架构 + 平台视野

试 LightRAG / GraphRAG 感受图谱检索；用 LangGraph 搭一个"检索→反思→再检索"的 Agentic RAG；docker 起一个 RAGFlow 或 Dify，对比平台与自研路线的取舍。

术语速查表

Embedding
把文本映射为高维向量，语义相近 → 向量距离近。常用：bge-m3、text-embedding-3
Chunking（分块）
长文档切成检索友好的小段。策略：固定长度 / 递归 / 语义 / 按文档结构，通常带重叠
Top-K
检索返回的片段数量，常见 4–10。太小漏信息，太大稀释上下文
混合检索（Hybrid Search）
向量语义检索 + BM25 关键词检索并行，用 RRF（倒数排名融合）合并结果
重排（Rerank）
用 cross-encoder 对粗排 top-50 精排出 top-5，公认的"性价比之王"升级
Faithfulness（忠实度）
RAGAS 核心指标：答案有多少比例能被检索上下文支撑（反幻觉程度）
Context Recall / Precision
该检索到的是否检索全 / 检索到的是否相关——分别定位召回与噪声问题
HyDE
先让 LLM 生成"假设性答案文档"，再拿它去做向量检索（答案比问题更像答案）
GraphRAG
抽取实体关系建知识图谱，检索沿图扩展——擅长关系型与"全局主旨"类问题
Agentic RAG
检索成为 Agent 的一个动作：规划查什么 → 执行 → 评估结果 → 决定是否再查
