Codex CLI：一个二进制，两种会话，都是 App Server 的客户端

交互式 codex 和非交互式 codex exec 都不自己跑模型循环。它们负责解析参数、拉起或连上 App Server、把线程协议翻译成终端。模型、工具、沙箱留在 server 后面的 core。

设计形状

用户敲的 codex 是 codex-cli 这个 crate 的二进制。它用 clap 做成一把多功能刀具：没有子命令时进入全屏终端；有子命令时，要么还是进同一套终端并带上内部标志，要么去做登录、诊断、MCP、沙箱这类一次性工作。

argv0 / argv1沙箱、补丁等别名
→
clap MultitoolCli子命令分发
→
TUI 或 exec两种客户端
→
App Server进程内或本机 socket
→
core线程、工具、沙箱
CLI 拥有终端参数、raw mode、批准框、退出码、更新交接
App Server 拥有会话thread/start、turn、审批请求、配置写回
core 拥有循环模型、工具执行、压缩、权限执行
交互和脚本共用协议，传输不同 TUI 的客户端名叫 codex-tui，session_source 写成 cli。它可以嵌一个进程内 server，也可以连已经在跑的本机 daemon，或者连 ws:// / unix:// 上的远程 server。codex exec 的 originator 是 codex_exec，并且总是 InProcessAppServerClient::start。脚本和这次进程同生共死，不依附后台 daemon。

进程还没起来时

main 第一件事是 arg0_dispatch_or_else。注释写明：希望只发一个可执行文件，又希望其中几项能力看起来像独立命令。Mac 和 Linux 用 argv0 模拟多个二进制，Windows 做不到硬链接别名，改用 .bat 包装。

分发发生在创建任何线程之前，因为接下来要改环境变量。

看到的名字实际跑什么
可执行文件名是 codex-linux-sandboxcodex_linux_sandbox::run_main，这个函数不返回
文件名是 apply_patch 或 applypatch补丁入口
第一个参数是 Windows MXC、exec helper、fs helper、Windows sandbox wrapper、core apply-patch对应的内部 helper，跑完直接退出
都不是从 ~/.codex/.env 加载环境，准备 PATH 别名，再进入正常 CLI

别名放在一个带锁的临时目录里，并插到 PATH 前面。锁文件保证这次进程活着时目录还在；进程结束后目录可以清掉。下次启动时，janitor 只删本机、本操作系统命名空间里已经解锁的旧目录。别的系统留下的目录和还被锁住的目录保留。别名创建失败只打印警告，CLI 继续跑，因为很多路径并不需要这些 helper。

真正的异步入口跑在名为 codex-main 的线程上，栈大小用 THREAD_STACK_SIZE_BYTES。注释说明 Runtime::block_on 会把顶层 future 放在调用者的 OS 栈上，所以他们把 runtime 放到这条受控线程里。Linux musl 的 x86_64 和 aarch64 构建把全局分配器换成 jemalloc。

子命令路由器

解析类型是 MultitoolCli。用法字符串是 codex [OPTIONS] [PROMPT]，或者 codex [OPTIONS] <COMMAND>。二进制即使以 codex-x86_64-unknown-linux-musl 这种平台名被调用，帮助文本也固定写成 codex。subcommand_negates_reqs 让子命令不必满足默认交互参数的必填项。

dispatch_cli 先做一批所有子命令共享的门禁，再按子命令分叉。门禁包括：worktree 是否被这个子命令支持、根上的 --strict-config 能不能传下去、--enable / --disable 折成配置覆盖。远程端点只留给会打开 TUI 的命令。exec、mcp、plugin 收到 --remote 会直接拒绝。

用户输入分发结果
无子命令，或 codex agents返回一个 future，等大块分发 future 结束之后再 poll。里面是交互式 TUI。agents 只是把 agents_overview 设为真
exec，别名 ecodex_exec::run_main。根上的 sandbox、model、cwd 通过 inherit_exec_root_options 继承下去
review现场组装一个 ExecCli，命令设成 ExecCommand::Review，再走同一条 exec
resume / fork把选择器、--last、会话 id 写进 TUI 的内部字段，然后还是 launch_tui
login logout mcp plugin doctor sandbox features update completion各自的一次性命令，跑完进程结束
app-server exec-server remote-control把同一份二进制当成服务进程。默认会话来源在 app-server 直跑时标成 VS Code
cloud，别名 cloud-tasks云任务浏览，以及把结果应用到本地工作区
apply，别名 a把 Codex 最近一次 diff 用 git apply 打到工作区
隐藏命令tcp-tunnel、git-credential、responses-api-proxy、stdio-to-uds、execpolicy。给 SSH、Git、内部代理用

交互式 future 被刻意留到 dispatch_cli 返回之后才 poll。注释写的是：先结束那个很大的子命令分发 future，再去 poll TUI 事件，避免两个大 future 叠在同一个栈帧上。

交互式路径

run_interactive_tui 做进入界面之前的检查：--no-daemon 和 --remote 不能一起用；prompt 里的 CR 归一成 LF；TERM=dumb 且没有 TTY 时直接拒绝，有 TTY 则警告并要求确认。然后 codex_tui::run_main。

TUI 的 run_main 立刻把活交给 startup_orchestration::run_main_inner，并用 boxed_future! 把这个大 future 移出调用者的栈。注释写明，Box::pin(large_future()) 仍可能在当前栈上按 future 的完整尺寸预留空间，所以他们用一个 #[inline(never)] 的函数先在别的帧里构造。

启动分阶段

startup_orchestration.rs 的模块注释把顺序说清楚了：轻量校验发生在占用终端之前。草稿 composer 出现之后，慢的配置加载和 App Server 初始化仍然要响应本地的安全编辑。

  1. 解析 -c、把 --search 映射成 web_search="live"、找到 CODEX_HOME。
  2. 在阻塞线程里 tui::init()，记下当时的屏幕尺寸，再建 StartupDraft。之后的慢操作都包在 startup_draft.run_until 里，输入不会被冻住。
  3. 决定 App Server 目标，加载配置、云配置、可选的 worktree、OSS provider。
  4. 需要时拉起本机 daemon，做版本兼容检查。
  5. 进入 run_ratatui_app：连接 server、查登录、可能跑 onboarding，然后进入会话。

发布构建里，如果这次启动没有初始 prompt，会先问要不要更新。用户选了更新，TUI 交还一个 UpdateAction 就退出。外层 handle_app_exit 在恢复终端之后再执行更新。daemon 更新会重新 exec 启动这次的 CLI 二进制，并带上 HANDOFF_ENV。更新因此发生在 raw mode 外面。

连哪一台 server

AppServerTarget 有四种：Embedded、LocalDaemon、Remote、Cloud。启动函数 app_server_target_for_launch 在前三种里选。Cloud 是同一枚举的另一种线程参数模式，本地状态库的初始化和远程工作区走一类分支。

条件目标
选了 workload identity强制 Embedded。这种身份必须配在远程 host 上，启动参数里再带远程地址会报错
显式 unix:// 指向默认控制 socketLocalDaemon，不允许失败后回退到进程内
其他显式 ws://、wss://、unix://PATHRemote。明文 ws:// 只在 localhost 上接受认证 token
没写远程地址，并且 50ms 内探到默认 socket，同时这次没有 CODEX_EXEC_SERVER_URLLocalDaemon，允许连接失败后回退 Embedded。共享 daemon 不能采纳这次进程自己的 executor 选择，所以带了 exec server URL 就改走进程内
探不到 socket先是 Embedded。若功能开关允许，后面还会尝试把 daemon 拉起来

自动拉起 daemon 还要同时满足：Unix 或 Windows、隐式连接、--no-daemon 没开，并且要么是 agents 总览，要么打开了 DaemonAutoStart。下面几种情况会留下 Embedded，并在界面上说明原因：

  • Windows 上这次进程是提权启动的。代码直接把 no_daemon 设上。
  • 还没登录，而 GCP 或 Gateway 的设置向导要用本次启动环境里的凭证。向导结束后会按所选 provider 重建嵌入式 server。
  • CODEX_HOME 在 WSL 的 drvfs 上。
  • Windows 这个启动器不允许脱离进程拉起。
  • daemon 的功能设置和这次客户端不兼容。兼容检查失败后目标被改回 Embedded。

连接函数 start_app_server 先按目标去连。只有 allow_embedded_fallback 为真的本机 daemon 失败时，才改目标为 Embedded 并重新初始化状态库。显式附着失败则把 hint 抛出去，要求 daemon 真的在。

进程内启动走 InProcessAppServerClient。required_human_approval 为真，客户端名 codex-tui，打开 experimental API。状态库只有 Embedded 会在这次进程里 try_init。初始化失败被包成 LocalStateDbStartupError。外层 run_tui_with_recovery 对可自动备份的损坏做一次：把坏文件移走，确认可以重建，然后重进 TUI。锁住的库只打印指引，不重试。同一个路径只尝试备份一次。

界面事件循环

app.rs 拥有 App 和高层 run loop。终端事件是 TuiEvent：按键、鼠标、粘贴、焦点、尺寸、Draw、Resume。服务端来的是 App Server 通知，批准、子代理活动、配置变更从这里进界面。

界面侧自己保留的状态包括：当前 ChatWidget、底部批准栏、resume 选择器、transcript overlay、文件搜索、keymap。模型要跑命令或改文件时，server 发批准请求，TUI 画选择框，人的决定再作为 RPC 写回去。TUI 不执行 shell。

panic hook 会先 tui::restore_after_exit，再把原来的 color-eyre hook 接回去。致命退出也会在返回错误前恢复终端，避免把用户留在 raw mode 里。

非交互路径

codex exec 的 clap 用法和顶层对称：codex exec [OPTIONS] [PROMPT]。子命令是 resume、fork，以及由顶层 review 塞进来的 review。没有子命令就是开一条新的非交互线程。

输入

prompt 可以是参数。参数是 - 或没给时从 stdin 读。stdin 是管道而且又给了 prompt，stdin 会包进一个 <stdin> 块追加进去。图片路径变成 UserInput::LocalImage。

输出

--json 用 JSONL 事件处理器，否则用人可读的 stderr 输出。-o 在 agent 启动前就打开最后一条消息的文件，避免沙箱里的活动把最终写入重定向走。

run_exec_session 的顺序是：按 human 或 JSONL 建 EventProcessor，需要时准备 OSS provider，确认当前目录在 Git 仓库里（--skip-git-repo-check 或 --dangerously-bypass-approvals-and-sandbox 可以跳过），然后启动进程内 App Server。

线程生命周期全部是协议调用：

  • 新会话：thread/start。非 ephemeral 时 history_mode 用分页。如果 server 回 -32600 说分页需要额外的 list 方法，客户端清掉 history mode 再试一次。
  • 恢复：先解析会话 id，再 thread/resume。
  • 分叉：thread/fork，exclude_turns 为真，模型仍带着线程上下文，响应里不必塞回全部历史。
  • 评审：先把目标收成 ReviewRequest，再作为这一次的初始操作。

随后客户端读 server 的通知，交给 EventProcessor。server 反过来要批准时，exec 在 handle_server_request 里处理。跑完调用 client.shutdown()，打印最终输出。中途见过错误就以退出码 1 结束。

exec 把“一次命令”收成“一轮” prompt、图片和可选的 JSON Schema 合成一次 UserTurn。进程等到这轮结束。交互式 TUI 则把同一条 thread/start 留在屏幕上，后面的每句用户输入都是新的 turn。两边的会话对象是同一个协议对象。

resume、fork、review

这三个看起来像独立产品入口，实现上是给两条现成客户端填内部字段。

命令内部变成什么
codex空的 TuiCli，打开新的交互线程
codex resumeresume_picker = true
codex resume --lastresume_last = true，不显示选择器
codex resume <id> [prompt]resume_session_id 设上，选择器关闭。后面的词成为这条线程的下一句
codex resume --all选择器仍在，关掉按 cwd 过滤，并显示目录列
codex fork ...同一组字段的 fork 版本。没给会话 id 又带 --worktree 会被拒绝，因为 worktree 需要明确的源会话
codex agentsagents_overview = true。不接受初始 prompt 和图片。远程模式下也不能附带本地 provider 或额外可写目录
codex review不进 TUI。合成 codex exec 的 review 子命令
codex exec resume|fork同一套线程 API，没有选择器，适合 CI

resume 和 fork 的这些字段标了 #[clap(skip)]。用户不能在裸的 codex --resume-last 上写它们，只能通过子命令包装器写入。这样帮助文本保持短，两条路径又共用一个 TuiCli。

参数怎么流下去

根命令和子命令各自有 clap 结构体，共享的模型、sandbox、cwd、图片、worktree 放在 SharedCliOptions。TUI 和 exec 各包一层，把其中几个参数标成 global，让它们出现在子命令后面仍然有效。根上的 -c 和 --enable 由 prepend_config_flags 接到子命令自己的覆盖列表前面。

TUI 还有一组只属于交互的开关：--ask-for-approval、--search、--no-alt-screen、--no-daemon、--strict-config。--dangerously-bypass-approvals-and-sandbox 和审批策略、auto review 互斥。exec 额外有 --json、--ephemeral、--output-schema、--ignore-user-config、--ignore-rules、--trust、--thread-source。

远程附着时，客户端不再把本地的额外目录和 sandbox_workspace_write.writable_roots 送过去。这些边界属于 server 那台机器。远程工作区的 cwd 只作为展示和会话目标覆盖，不拿来加载本机项目配置。

--oss 在 TUI 启动中段处理。没指定 provider 时先探测本地 Ollama 和 LM Studio，必要时把终端暂时交还，弹出选择。选中的 provider 写进 model_provider 覆盖，再交给嵌入式 server，这样之后工作区要求被拿掉时，启动时的选择还在。取消选择会以错误结束启动。

进程上的约束

  • 单二进制多角色。发布物是一个 codex。沙箱 helper、补丁器和若干内部服务靠 argv0、argv1 或子命令进入，避免用户安装一串可执行文件。
  • 大 future 不叠在同一帧。分发、TUI 启动、嵌入式 server 启动都用 Box::pin 或 boxed_future! 挪走。这是这个 CLI 里反复出现的工程注释，说明会话状态已经大到会撑爆默认栈。
  • 终端所有权有守卫。进入 alt screen 之前初始化，退出、panic、致命错误都走恢复。更新和确认提示发生在 raw mode 之外。
  • 本地状态库失败可恢复一次。损坏走备份后重建；锁冲突只提示。避免一个坏的 SQLite 让每次启动都循环备份。
  • daemon 是优化，嵌入是退路。多个终端可以共享一个后台 server。任何身份、文件系统、提权或版本对不上的情况，都退回这次进程自己的 server，并告诉用户为什么。
  • 退出码分层。TUI 的致命信息先打印再 exit(1)。exec 在事件流里见过错误也以 1 退出。用户主动离开是成功退出。App Server 若返回 Forced，CLI 直接 exit(0)，注释说明 runtime 拆除可能永远等在被堵住的 rollout I/O 上。

读代码时的顺序

要对着仓库把这条链走完，按这个顺序开文件就够。都在 codex-rs 下面，对应 2026-11-11 的 main。

  1. arg0/src/lib.rs：arg0_dispatch 和 arg0_dispatch_or_else。看一个文件如何变成沙箱 helper。
  2. cli/src/main.rs：MultitoolCli、Subcommand、main、dispatch_cli、finalize_resume_interactive、handle_app_exit。
  3. tui/src/cli.rs：哪些字段是用户旗帜，哪些是子命令偷偷写入的。
  4. tui/src/lib.rs：AppServerTarget、start_app_server、app_server_target_for_launch、run_main。
  5. tui/src/startup_orchestration.rs：草稿 composer、daemon 自动启动、退回嵌入式的条件。
  6. tui/src/app.rs：TuiEvent 怎么和 server 通知汇合。
  7. exec/src/cli.rs 和 exec/src/lib.rs：run_main、run_exec_session、start_thread。

材料是当天从 openai/codex 的 main 读到的源码，提交时间在 2026-11-11。函数名和分支条件会随版本变。产品层的仓库介绍仍在同目录的 Codex调研报告.html。
