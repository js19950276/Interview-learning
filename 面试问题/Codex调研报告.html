一分钟结论

这个仓库的价值在 harness，也就是包住模型的那层运行时。模型负责决定下一步，仓库负责把决定变成可恢复、可缓存、有权限边界的本地动作：读仓库、改文件、跑命令、接外部工具，并在越界时停下来问人。

本地优先CLI 在你的机器上跑。云端任务是另一条产品线
Rust 单仓核心、TUI、沙箱、协议、SDK 都在 codex-rs
两层安全沙箱规定做得到什么，审批规定什么时候要问
先记住这个分界 官方文档把 Codex 定义成一整套软件 Agent：CLI、桌面里的体验、IDE、云端任务。开源仓库是其中本地执行和客户端协议的家。openai/codex 不接受外部代码 Pull Request。社区贡献走 Issue：复现、日志和根因分析。实现由 Codex 团队自己改。

三个 Codex

同名东西叠了三代。面试里先把它们拆开，后面的架构才对得上仓库。

它是什么和这个仓库的关系
2021 年的 Codex 模型 基于 GPT-3、面向代码微调的模型，早期 GitHub Copilot 用过它 权重和训练代码不在这个仓库。它是名字的来源，API 后来下线
2025 年 4 月起的 Codex 产品 编程 Agent 套件：终端、IDE、桌面、云端任务。工程博文写明 CLI 于 2025 年 4 月首次发布 仓库创建于 2025-04-13。README 现在的自我介绍是 “Lightweight coding agent that runs in your terminal”
openai/codex 这个仓库 本地 Agent 的开源实现，外加 Python / TypeScript SDK 和 App Server 默认分支 main。稳定发布走 rust-v* 标签。查询时最新稳定版是 0.167.1

模型名会换。2026 年 1 月的工程博文还拿仓库里的 gpt-5.2-codex 提示词举例。2026 年 11 月的文档把 gpt-6.1-sol 写成账户有权限时的默认起点，把 gpt-6-luna 写成更快、更便宜的轻任务选项。仓库提供的是可切换的模型客户端，模型目录本身跟着账户和日期变。

仓库怎么长

顶层是一个同时有 Cargo、Bazel、pnpm 和 Nix 的单仓。人真正每天跑的二进制在 Rust workspace 里。npm 上的 @openai/codex 只声明了一个 bin/codex.js，用来把人带到原生可执行文件。

路径角色
codex-rs/coreAgent 循环、会话、压缩、shell、补丁、MCP、安全策略。源码里能直接看到 session/、compact.rs、exec_policy.rs、tools/
codex-rs/cli、tui命令行入口和终端界面
codex-rs/app-server*协议、传输、daemon、客户端。IDE 和 SDK 接的是这一层
codex-rs/linux-sandbox、windows-sandbox-*、bwrap、sandboxing按操作系统拆开的命令隔离
codex-rs/exec、exec-server非交互执行，以及把执行再服务化
codex-rs/code-mode*另一条执行宿主。App Server 可以挂本地或远程 Code Mode host
sdk/Python 与 TypeScript SDK。Python 侧通过 JSON-RPC 控制本机 App Server，发布包会钉住一份 Codex CLI runtime
codex-cli/npm 包装。真正的实现在 Rust 侧
docs/仓库内文档大多改成跳转到现行文档站。贡献说明、从源码构建、开源基金页还留在仓库里

工具链钉在 Rust 1.95.0，组件含 clippy、rustfmt、rust-src。仓库根的 Node 要求是 24.22.1 以上，包管理器是 pnpm 10.34.5。从源码构建的路径是进 codex-rs，cargo build，再用 cargo run --bin codex。日志走 RUST_LOG。

构建系统是双轨的 本地文档教你用 Cargo 和根目录的 just。仓库同时提交了 MODULE.bazel、BUILD.bazel 和大量 Bazel 规则。发布物很多：一次 GitHub Release 会打出各平台二进制，macOS arm64 常用的包是 codex-aarch64-apple-darwin.tar.gz，Linux x86_64 常用 musl 包。安装脚本默认从 releases.openai.com 拉，失败再回退 GitHub Releases。

Agent 循环

2026 年 1 月 23 日，Michael Bolin 的工程文《Unrolling the Codex agent loop》把这条循环写公开了。文中说它是 CLI、云端和 IDE 共用的 harness。到 2026 年 11 月，仓库又长出了子代理、插件、Code Mode、实时语音和 guardian 审查，循环的骨架还在：一次用户消息是一个 turn，turn 里面可以有许多次推理和工具调用，直到模型给出 assistant message，控制权回到人。

用户输入一个 turn 的起点
→
拼 prompt指令、工具、历史
→
Responses APISSE 流式返回
→
工具调用shell、补丁、MCP…
→
结果写回成为下一跳的前缀

一轮里有很多次推理

CLI 把请求发到 Responses API。ChatGPT 登录走 https://chatgpt.com/backend-api/codex/responses。API key 走 https://api.openai.com/v1/responses。端点可换：兼容 Responses API 的 Azure、以及 --oss 时的本机 Ollama 或 LM Studio。模型要么给出给用户看的话，要么发出工具调用。Agent 执行工具，把输出追加进 input，再请求一次。循环停在 assistant message。对编程 Agent 来说，真正的产出常常是磁盘上的 diff，这句话只是这一轮的终止信号，例如 “我把你要的 architecture.md 加上了”。

线程会越来越长。下一轮的 prompt 带上此前的消息、推理摘要和工具调用。上下文窗口同时吃输入和输出，所以窗口管理是 harness 的职责，不是模型自己的事。

无状态请求和缓存

整段对话里，发往 API 的 JSON 体量按轮次是平方级的：每一跳都重发越来越长的前缀。Responses API 有 previous_response_id 可以少传历史。Codex 当时不用它。原因写在文里：每个请求保持无状态，才能服务 Zero Data Retention。ZDR 客户的推理链用 encrypted_content 带在请求里，服务端能解密，OpenAI 保存的是解密密钥，不保存客户数据。对应改动在 PR #642 和 #1641。

采样成本远大于网络成本，所以性能押在 prompt cache 上。缓存只命中精确前缀。静态内容放前面，会变的内容放后面。工具列表也必须逐字一致。文中点名三类会打掉缓存的操作：

  • 对话中途改可用工具。早期 MCP 支持曾因工具枚举顺序不稳定造成缓存失效，后在 PR #2611 修掉。MCP 的 notifications/tools/list_changed 如果在长对话中途兑现，也会造成一次昂贵的 miss。
  • 中途换模型。模型专属指令位于 prompt 前部，一换就整段失效。
  • 中途改沙箱、审批或当前工作目录。

能追加就不改写。沙箱或审批变了，就再插一条同样格式的 permissions instructions。工作目录变了，就再插一条 environment_context。旧前缀保持不动。

上下文压缩

窗口快满时，Codex 用压缩换继续干活的能力。早期实现是用户手动 /compact：拿整段对话加一份摘要指令再请求一次，用返回的 assistant message 当新的 input，见 PR #1527。后来改走 Responses API 的 /responses/compact。它返回一组更短的 item，其中有一条 type=compaction，用密文保住模型对原文的潜在理解。超过 auto_compact_limit 时自动触发。0.167.0 的修复说明写着：自动压缩现在会把失败响应和缺少 token 用量的响应所保留的输出也算进去。

提示词怎么拼

用户看到的是一句任务。发往 Responses API 的是三块：instructions、tools、input。服务端再把它们排成模型真正看到的序列。前三项的顺序由服务端定，其中 system message 的内容也由服务端定；工具和 instructions 的内容由客户端定。

instructions

优先读 ~/.codex/config.toml 里的 model_instructions_file。否则用该模型捆绑的 base instructions。模型提示词打进 CLI 二进制。

tools

2026 年 1 月的例子里有本地 shell、update_plan、Responses API 的 web_search，以及用户 MCP 工具，名字形如 mcp__weather__get-forecast。

input 在用户消息之前，按这个顺序放：

  1. 开发者消息：权限。只描述 Codex 自己的 shell 工具受到的沙箱和审批。模板来自仓库里的 Markdown 片段，例如 workspace write 和 on-request。MCP 工具不在这个沙箱里，它们自己负责边界。
  2. 可选的开发者消息。来自配置里的 developer_instructions。
  3. 用户指令，角色仍是 user。从多处拼起来，越具体的越靠后：$CODEX_HOME 里的 AGENTS.override.md 或 AGENTS.md；从 Git 根走到当前目录，每层至多一份，默认合计 32 KiB；然后是已配置技能的短前言、每条技能的元数据，以及怎么调用技能。
  4. 环境。<cwd> 和 <shell>。
  5. 用户这次真正说的话。

到 2026 年 11 月，core/src/tools/handlers 里的工具面已经比博文里的四件套宽。能对上名字的包括 apply_patch、unified_exec、plan、mcp、mcp_resource、multi_agents、request_user_input、request_permissions、view_image、tool_search、sleep、current_time，以及插件安装、上下文剩余量、新上下文窗口。博文是循环的设计说明，工具表以当天源码为准。

沙箱和审批

文档把两层控制写成互相配合的东西。沙箱决定命令在技术上碰得了哪些文件和网络。审批策略决定什么时候必须停下来问人。默认本地运行是：网络关闭，写入限制在当前工作区，命令越界才询问。

read-only

可以看文件。改文件和跑命令要先批准。适合只想聊天或做计划。

workspace-write

默认可写工作区，可跑工作区里的常规命令。网络默认仍关。这是本地低摩擦档。

danger-full-access

去掉文件系统和网络边界。和 approval_policy = "never" 合在一起就是完整访问。

审批策略

  • on-request：沙箱内的动作直接做，越界再问。和 workspace-write 配在一起，是文档里的低风险自动化预设。
  • never：不再弹出批准。
  • untrusted 作为可选审批策略已经退役。旧配置里留着它，客户端可能直接起不来。想保留“命令都要问”的效果，应在用户级配置里把项目标成 trust_level = "untrusted"。这样还会跳过项目本地配置。
  • approvals_reviewer 可以选择 user 或 auto_review。自动审查只处理已经需要批准的动作，不放宽沙箱。沙箱内允许的动作不会再送去审查。

操作系统怎么强制

平台实现
macOS系统自带的 Seatbelt。开箱即可用。
Linux 与 WSL2优先用 PATH 上的 bwrap 做文件系统和命名空间隔离。之后在进程内设置 PR_SET_NO_NEW_PRIVS 并装 seccomp。没有 bwrap 时回退到随包的 helper，并在启动时警告。WSL1 建不了需要的 user namespace，会拒绝进入这条沙箱路径。
Windows原生沙箱。文档建议在设备和策略允许时优先 MXC，elevated 作为旧实现的回退。

Linux 沙箱 README 写明：文件系统默认 --ro-bind / /，可写根再用 --bind 打开。可写根下面的 .git、.codex 等保护路径会重新标成只读。路径越具体的规则越后套，所以可以写成“仓库可写、中间一层拒绝、更里面一层再打开”。旧的 Landlock 实现还留在 src/seccomp.rs 一带，但文件系统受限策略会拒绝它，原因是它隔离不了 App Server 的 Unix socket。限制网络的策略会挡网络 syscall；即便网络放开，也会挡 AF_VSOCK。所有过滤模式都挡 io_uring，避免绕过套接字家族限制。

沙箱罩住的是命令，罩不住所有工具 工程文写明，权限说明只约束 Codex 提供的 shell。MCP 服务器不在这个沙箱里。2026 年 11 月的文档补了两层：带破坏性标注的 App / MCP 工具调用仍然要批准；network_proxy 只过滤沙箱里的脚本、程序和子进程，不过滤网页搜索、连接器、MCP、浏览器和 Computer Use。网络默认关闭，网页搜索默认走缓存索引而不是现场抓活页面，都是同一条思路：少把任意外部内容直接送进一个能改你磁盘的循环。

打开命令网络后，还可以把 features.network_proxy 打开，用域名规则约束出站。deny 压过 allow。默认拒绝回环、链路本地和私网地址。解析到私网 IP 的主机名即使匹配允许列表也会被挡。这是尽力而为的 DNS 重绑定防护，文档写明它不能单独消灭重绑定，敌对 DNS 在威胁模型里时还要在更低层做出站控制。

GPT-6 Astra 另有异步的安全监控，发现可疑模型行为可以暂停任务。监控可以晚于触发它的那个动作到达，所以它是沙箱、权限和人工复查之外的一层，不能替代它们。CLI 和移动端拿不到完整 findings 和恢复流程，任务会直接结束。零数据保留、修改后的滥用监控，或非美国数据驻留，同样不能走这套恢复。

配置和项目指令

用户配置在 ~/.codex/config.toml。项目可以放 .codex/config.toml。CLI 和 IDE 共用这些层。项目层只有在项目被信任时才加载。把项目标成不受信任后，项目本地的配置、hooks 和 rules 都会跳过，用户级和系统级仍然生效。

优先级从高到低：

  1. CLI 标志和 --config
  2. 受信任项目里的 .codex/config.toml，从项目根走到当前目录，越近越优先
  3. --profile 选中的 ~/.codex/<name>.config.toml
  4. 用户配置 ~/.codex/config.toml
  5. 登录工作区下发的云托管默认值
  6. 系统配置，Unix 上是 /etc/codex/config.toml
  7. 内置默认

企业环境里还有更高的 requirements.toml，可以禁止 approval_policy = "never" 或 sandbox_mode = "danger-full-access"。要求约束行为，配置提供默认值。本地执行时，MDM 和旧的托管设备要求高于 Agent Security，设备上的系统要求文件低于 Agent Security。

AGENTS.md

每次启动拼一条指令链。全局只取 Codex 主目录里第一份非空文件，AGENTS.override.md 优先于 AGENTS.md。项目从 Git 根走到当前目录，每层至多一份，查找顺序同样是 override、AGENTS.md、配置里的 fallback 文件名。拼接时根在前、当前目录在后，所以越靠近工作目录的文件越能覆盖前面的说法。空文件跳过。合计到达 project_doc_max_bytes（默认 32 KiB）就停止。

网页搜索的四种模式

  • cached：默认。结果来自 OpenAI 维护的索引，不去抓任意活页面。
  • indexed：外部访问要先过搜索索引的门。
  • live：现场抓取，等价于 --search。完整访问沙箱下，网页搜索会默认改成这一档。
  • disabled：关掉这个工具。

技能、MCP、子代理

Skills

把可重复的做法收成技能。启动时只把元数据和一段用法放进用户指令，需要时再展开。自定义提示词这条旧路径，文档已标成弃用，让位给技能。

MCP 与插件

codex mcp 添加本地或远程服务器，先看清当前会话真正暴露了哪些工具。0.167 前后的提交还在做会话级插件覆盖、共享 MCP 连接的租约，以及插件推荐缓存。

子代理

当前本地版本默认可以派子代理。CLI 用 /subagents 查看和切换。主线程收回的是摘要。每个子代理自己消耗模型和工具，总 token 高于单代理。

子代理的设计理由写在文档里，核心是保护主线程。主线程留着需求和决定。探索、测试日志、堆栈这些吵的中间结果放到旁边的线程，最后只交摘要回来。文档引用了 Chroma 对 context rot 的讨论：窗口变大之后，不相关的细节仍会把有用信息埋掉。读多写少的活适合并行，例如勘探、测试、分诊、摘要。多个代理同时改代码容易冲突，协调成本上去之后就不划算。

子代理默认继承父代理的模型和推理力度。也可以在提示里点名，或在 config.toml 的 [agents] 里给自定义代理写死。文档的例子是用 gpt-6-luna 做快扫描，用更高力度的 gpt-6.1-sol 做需要规划和验证的多步工作。AGENTS.md 或技能也可以要求委派，所以“要不要开子代理”可以写进仓库约定，而不只是每次口头说。

App Server 和 SDK

两条可编程入口，文档把用途拆开。要在 CI 里跑完一个任务，用 SDK。要做自己的客户端，处理登录、历史、批准和流式事件，用 App Server。codex mcp-server 和独立的 codex-mcp-server 二进制已经移除，旧集成迁到 App Server。

协议

codex app-server 使用 JSON-RPC 2.0，线上消息省略 "jsonrpc":"2.0"。传输有四种：默认 stdio 的换行 JSON；实验性的 WebSocket；Unix socket；以及 --listen off。先发 initialize，再发 initialized 通知，然后 thread/start 和 turn/start。请求带 id，通知没有 id，例如 turn/started、turn/completed。可以用 CLI 导出与当前版本严格对应的 TypeScript schema 或 JSON Schema。

远程 TUI 的接法是一台机器上 codex app-server --listen ws://127.0.0.1:4500，另一边 codex --remote ws://127.0.0.1:4500。非本机要上 TLS 和 bearer token，token 放环境变量，用 --remote-auth-token-env 传入名字。WebSocket 在非回环地址上曾经默认不鉴权，文档要求暴露到远端之前先配 --ws-auth。队列满时返回 JSON-RPC -32001，客户端按指数退避重试。

SDK 长什么样

from openai_codex import Codex, Sandbox

with Codex() as codex:
    thread = codex.thread_start(
        model="gpt-6.1-sol",
        sandbox=Sandbox.workspace_write,
    )
    result = thread.run("Make a plan to diagnose and fix the CI failures")
    print(result.final_response)

Python 要求 3.10+。AsyncCodex 给已经是异步的程序。thread.run() 可以接着说。thread_resume 在 CLI 0.166 之后会沿用线程保存的模型提供方；要换提供方就 thread_fork。沙箱预设是 read_only、workspace_write、full_access，传给某一次 run 会作用于这一轮以及之后。外部系统塞进来的内容用 ExternalMessage，Codex 把它当成工具输出，优先级低于用户和开发者指令。

TypeScript 侧是 new Codex()、startThread()、thread.run()。结构化配置走 config，表达不了的键用 configOverrides 传原始 TOML。这些覆盖只影响这一次进程，不改你的配置文件。

开源边界

docs/contributing.md 写得很直。Issue 欢迎：缺陷、复现、日志、根因分析和功能需求。外部代码和 Pull Request 不收。给出的理由是，有效改动依赖架构上下文、系统约束和路线图；外部 PR 常常打在低优先级或小众问题上，评审成本高于团队自己改。他们把“想清楚问题”看成难的部分，实现则可以靠 Codex 自己完成。

docs/open-source-fund.md 写的是 100 万美元计划，单项最高 25,000 美元 API credits，滚动评审。申请页是 OpenAI 的表单。

现行的维护者计划

安全问题走 SECURITY.md，不进公开 Issue。安装文档列的系统要求是 macOS 12+、Ubuntu 20.04+ / Debian 10+，Windows 11 通过 WSL2。内存最低 4 GB，建议 8 GB。Git 2.23+ 用于内置的 PR 辅助，可选。

可以带走的判断

  1. 把 harness 和模型分开讲。换模型只换 instructions 和端点。会话、工具协议、沙箱、压缩和缓存纪律留在 Rust 里。这是这个仓库比“一个会写代码的 API”厚的地方。
  2. 请求无状态，缓存靠前缀不动。不用 previous_response_id 是为了 ZDR。代价是每跳重发历史，所以任何会改写 prompt 前部的功能都要先想缓存。中途变化用追加消息表达。
  3. 安全是两层，而且罩不住全部工具。操作系统沙箱管 shell。审批管越界。MCP、浏览器和网页搜索要另算。默认断网、网页搜索走缓存，是在降低提示注入直接碰到一个能写磁盘的循环的机会。
  4. 压缩是协议能力。从“让模型写一段摘要”走到 /responses/compact 的密文 item，是为了在缩短窗口的同时留住模型已经形成的理解。
  5. 子代理首先是上下文卫生。并行加速是附加效果。主线程被日志灌满之后，更大的窗口也救不了质量。
  6. 客户端做薄。TUI、IDE、SDK 共享 App Server 和 core。要嵌进自己的产品，接 JSON-RPC，而不是再写一个循环。
  7. 信任是配置的一部分。项目级 .codex/ 只有受信任仓库才加载。不受信任的仓库不该靠一份本地 TOML 改写审批和沙箱。
  8. 开源范围要说准。本地运行时、协议和 SDK 在这个仓库。IDE 插件和云端任务环境不在。社区可以报问题和做根因分析，代码由内部改。这是产品仓库的开源方式，不是典型的社区共建运行时。
