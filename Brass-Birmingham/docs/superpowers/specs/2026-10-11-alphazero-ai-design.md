## 1. 文档目的

本文固定「人机对弈 AI」子系统的完整设计:算法形态(MCTS + 神经网络自博弈训练)、技术栈、引擎层改造边界、训练管线、App 接入方式与分阶段验收标准。实现计划必须以本文为依据;游戏规则冲突时以 RULES.md 为准。

## 2. 已确认决策

以下决策已经作者确认,是本文的前提,不再作为开放问题:

| 决策点 | 结论 |
|---|---|
| AI 形态 | AlphaZero 式:自博弈训练策略/价值网络,对局时 MCTS 由网络引导 |
| 技术栈 | Swift 引擎单源(自博弈 CLI 复用 GameCore 源码)+ PyTorch 训练 + CoreML 端上推理 |
| 隐藏信息 | V1 完美信息搜索(搜索与网络输入可见对手手牌、牌堆顺序),后续可升级采样决定化 |
| 支持人数 | **先只做 4 人局**(单机 = 1 人 + 3 AI;多人房 = 真人 + AI 补足 4 席);2/3 人局暂缓,价值头仍为每玩家向量,后续开放只需补自博弈数据 |
| 接入方式 | 单机对 AI 模式 + 多人房 AI 补位两种都要 |
| 引擎双写 | 禁止。规则引擎、状态编码器只有 Swift 一份;Python 只消费已编码张量 |

## 3. 总体架构

```
┌─ 训练期(Mac,离线)────────────────────────────────────┐
│  selfplay CLI(SwiftPM,直接编译 GameCore/ 源文件)      │
│    ↓ 多进程并行跑自博弈对局                              │
│    ↓ 每步:枚举动作 → MCTS → 访问分布 + 选择的动作        │
│    ↓ 叶子评估:本地推理服务(PyTorch,动态 batching)      │
│    ↓ 产出训练分片:特征张量(f16)+ 策略目标 + 终局排名   │
│  training(Python/PyTorch)→ checkpoint                 │
│    ↓ 竞技场门控:新模型 vs 现任,胜率 >55% 才晋级         │
│    ↓ 晋级 checkpoint 导出 CoreML → 打包进 App           │
└────────────────────────────────────────────────────────┘
┌─ 运行期(App 内,宿主设备)──────────────────────────────┐
│  AIPlayerDriver(actor,挂在宿主会话上)                  │
│    ↓ AI 座位成为行动方时:枚举动作 → MCTS                │
│    ↓ 叶子评估:CoreML 推理(或启发式评估函数降级)        │
│    ↓ 以普通 PlayerIntent 提交 HostEngine                │
│  事件流、投影、远端客户端零改动                           │
└────────────────────────────────────────────────────────┘
```

**防漂移三原则**:

1. 规则引擎只有 Swift 一份;训练 CLI 通过 SwiftPM 相对路径编译同一批源文件,不复制、不移动。
2. 状态编码器只有 Swift 一份;自博弈把编码结果写进训练数据,Python 永远不接触 `GameState`。
3. 模型权重只有 PyTorch 一份;App 消费的 CoreML 模型是晋级 checkpoint 的机械转换产物,转换脚本幂等可重现。

## 4. 引擎层改造(GameCore 内,不动规则语义)

### 4.1 FastActionEnumerator

**职责**:给定 `GameState` 与行动玩家,枚举其全部完整合法动作,输出 `[PlayerIntent.Payload]`(不含 `retractTurnActions`/`confirmEraIntermission`,前者 AI 永不使用,后者由驱动器自动处理)。

**实现方式**:以 `LegalActionQueryEngine.respond` 的逐步 `nextChoices` 做 DFS,遇 `completePayload` 即收;同一 draft 分支去重用结构相等(值比较),不计算 `draftDigest`(现有 JSON 摘要逐节点编码,速度不满足模拟量级)。为此给查询引擎增加"无摘要快速路径"参数,行为不变、仅跳过摘要计算。

**搜索爆炸控制**:Brass 单决策完整动作可达数百个(卡 × 动作 × 目标 × 资源来源组合)。枚举器提供 `limit` 与 `priorOrdering` 参数:超出上限时按调用方给的先验排序截断(自博弈与实战均用网络先验排序取 top-K;无网络时按内置启发式排序)。**枚举本身必须完备无截断的模式保留**,供测试做全量对拍。

**正确性契约**(P0 验收核心):

- 完备模式下枚举出的每个 payload,逐一提交 `HostEngine.submit` 必须全部 `.accepted`;
- 枚举数量与 `ExactCompletionSearch` 的可达性判定交叉验证(逐 draft 路径对照);
- 强卖阶段(`turnPhase == .forcedSale`)同样可枚举;时代结算阶段无可枚举动作,返回空。

### 4.2 SimulationRunner

**职责**:模拟专用"瘦提交"路径:`apply(_ payload:, to state: inout GameState)`,直接调用 `GameRulesEngine.resolveX` 系列解析器推进状态,跳过 `HostEngine.submit` 中的身份校验、`GameStateAuthorityValidator` 全量校验与投影构建——这些是宿主防错机制,模拟中不需要且是主要开销。

规则解析逻辑一行不改;`resolveX` 返回的事件在模拟中被丢弃。终局判定复用 `turnPhase == .ended` 与 `finalStandings`。

### 4.3 不变量

- 本节所有新代码放在 `GameCore/Simulation/` 或独立模块,不修改任何现有 `Rules/*.swift` 的规则语义;
- 模拟路径与宿主路径的状态推进必须等价——用随机状态对拍测试锁定:同一 payload 序列,`HostEngine.submit` 与 `SimulationRunner.apply` 产出的 `GameState` 逐字段相等。

## 5. 状态编码(StateEncoder,Swift,版本化)

**输入**:`GameState` + `VerifiedGameDataCatalog`。**输出**:扁平 `Float32` 数组,固定长度,由 `featuresVersion: Int` 锁定;布局改变必须递增版本,旧训练数据随之作废,不得静默变更。

**布局表**(维度依据已核实的数据:v2018.11 规则集,27 位置 / 49 产业槽 / 39 路线 / 9 商人槽 / 31 卡牌定义 / 6 产业 / 煤市场 14 格 / 铁市场 10 格 / 收入表 100 档):

| 区块 | 内容 | 维度 |
|---|---|---|
| 全局 | 时代 one-hot(2)、回合数、剩余动作数、人数、阶段 one-hot(4)、牌堆余量、万能池余量×2、活跃玩家 one-hot(4)等 | ~20 |
| 玩家 ×4 | 现金、收入档、VP、已花费、剩余链接、手牌 31 维计数(完美信息:四家手牌都编码)、产业堆余量 6×4(产业×等级)、私有弃牌 31 维 | ~100/人 ≈ 400 |
| 产业槽 ×49 | 归属 one-hot 5(4 玩家+空)、产业 one-hot 7(6+空)、等级、已翻转、资源数、已结算市场配送 | ~15/槽 ≈ 735 |
| 路线 ×39 | 归属 one-hot 5、时代 2、存在位 1 | 8/条 = 312 |
| 商人 ×9 | 商人定义 one-hot 9(8+空)、有啤酒 | 10/槽 = 90 |
| 市场 | 煤 14 格(有立方、价格)、铁 10 格、£8/£6 无限价标记、公共供应煤/铁/啤酒量、替代位 | ~35 |
| 牌信息 | 公共弃牌 31 维计数、牌堆组成 31 维计数(完美信息) | 62 |

合计约 1,650 维,首版以实现时生成的布局清单为准(`StateEncoder.layoutManifest` 输出各区块名称与偏移,golden 测试锁定总长与采样值)。

**数值规范**:计数类除以合理上限归一;金额类 /200;一律 Float32;NaN/Inf 禁止(测试断言)。

**Golden 测试**:固定种子生成对局,逐步编码,记录张量 SHA256;任何布局或数值变更导致哈希变化,必须伴随 `featuresVersion` 递增。

## 6. 神经网络结构(PyTorch)

| 部件 | 规格 |
|---|---|
| 输入 | `[1, featuresVersion 对应维数]` 的 multiArray |
| 主干 | 小 ResNet:MLP 形态 8 残差块 × 128 宽(牌类游戏无空间卷积需求,MLP 残差块即可;后续可试验按位置/路线分组的结构化分支) |
| 价值头 | 线性 → 每玩家向量(4 维),softmax 归一为排名效用分布;实际人数之外的维被 mask |
| 策略头 A | 动作类型分布:8 维(GameAction 7 种 + 强卖) |
| 策略头 B | 卡牌定义分布:31 维(按 definitionID 固定序) |
| 参数量 | ~1M 量级,CoreML 单次推理 1–3ms(Apple Silicon 实测目标) |

**策略目标的设计**:MCTS 访问分布按两个因子分解——每个被访问动作恰属于一个动作类型和一个卡牌定义,访问数可无歧义地汇总为 8 维动作类型分布与 31 维卡牌分布,训练目标即这两个分布(温度调整后的访问占比)。这样训练侧完全没有"变长动作空间"问题;目标选择(具体位置/线路/资源来源)的先验 V1 不由网络给出,由 MCTS 搜索自行细化。V2 若加目标头(如 build 位置 49 维、network 路线 39 维等分头),训练数据格式已兼容(每因子独立向量),不破坏分片格式。

**价值标签**:终局 `finalStandings` 中玩家排名 r(并列同组),n 为人数:`v = (n − r) / (n − 1)`,两人局即胜 1 / 负 0。

## 7. MCTS 设计

- **算法**:PUCT。选择公式 `a* = argmax Q(s,a) + c_puct · P(s,a) · √N / (1 + N(a))`;根节点 Dirichlet 噪声(α=0.3,权重 0.25)。
- **先验**:`P(s,a) ∝ 策略头A(动作类型) × 策略头B(卡牌定义)`,在枚举出的合法动作集上归一;无网络降级时用内置启发式先验(见 §7.3)。
- **多人备份**:MaxN 式——每个节点维护每玩家价值向量,展开沿"当前行动玩家"视角取最大;叶子价值来自价值头(或终局排名效用)。这是多人 MCTS 的标准处理。
- **动作空间控制**:每节点保留 top-K 子女(K=32,可调),按先验排序;超出部分本次搜索不展开(progressive widening 的截断变体,实现简单且够用)。
- **温度**:自博弈前 1/3 步 τ=1 按访问分布采样(保证数据多样性),之后 τ→0 贪心;实战 τ=0。
- **特殊阶段**:
  - 强卖:枚举强卖意图,仅用价值头评估(无策略先验),走同一树搜索;
  - 时代结算确认:非决策点,驱动器直接确认;
  - 撤回:AI 永不撤回,也不响应人类的撤回(撤回只影响人类座位)。
- **预算**:
  - 自博弈:~300 模拟/步(推理服务动态 batching 吸收并行对局的请求);
  - 端上按难度:轻量 100 / 标准 300 / 深思 800 模拟,单步目标 ≤5s(深思档),超标自动截断;
  - 所有搜索可取消(Task 取消传播到推理调用)。

### 7.1 降级路径:启发式评估函数

模型缺失、加载失败或用户选"无网络 AI"时,叶子评估退化为线性启发式:

```
score(p) = 0.01·cash + income等级表查值(收入档→期望未来现金流折现)
         + 1.0·VP + 0.5·产业槽存在价值(未翻转产业按等级加权)
         + 0.3·已建链接价值 + 0.2·手牌张数
```

权重初值人工设定,不训练(Phase 1 交付物,独立可用);上线网络模型后仅作兜底。归一化到排名效用尺度后进入同一备份流程。

### 7.2 树实现注意

- 节点存动作子集(枚举器 top-K 输出)与统计(访问数、每玩家价值和),不存完整状态副本——状态在下降时增量重放(每步一次 `SimulationRunner.apply`,COW struct 复制成本可控);
- 不做转置表(V1 不引入 Zobrist 哈希);若性能分析显示重复局面占比高,再列为独立优化项。

## 8. 自博弈管线(tools/selfplay/,SwiftPM)

### 8.1 包结构

```
tools/selfplay/
  Package.swift          ← target 源码用相对路径指向
  Sources/SelfPlay/        ui-prototype/IndustrialCityBirmingham/GameCore/**
                           ui-prototype/IndustrialCityBirmingham/GameData/**
                           (SwiftPM path 跨目录引用,文件不移动不复制)
```

App target 继续按现状直接编译这些文件;CLI 与 App **不互相链接**,只是编译同一份源码。Xcode 工程与现有构建流程零改动。

### 8.2 自博弈流程

1. 进程启动参数:模型服务地址、对局数、人数固定 4(2/3 人局暂缓)、随机种子、输出目录;
2. 每局:`SetupRules` 建局(种子派生自进程种子),循环至终局:当前行动方视角编码状态 → 枚举动作 → MCTS → 记录 `(features, 策略目标A, 策略目标B, chosenActionKey, 玩家视角)` → `SimulationRunner.apply`;
3. 终局把 `finalStandings` 折算成每局一条价值标签,回填该局全部样本;
4. 写分片:自描述二进制格式——文件头(magic、featuresVersion、布局哈希)+ 样本记录(定长头 + f16 特征 + f32 目标向量),单分片 ~2k 样本;**格式带版本头,旧数据可被训练侧识别并拒绝混用**;
5. 可复现性:相同种子 + 相同 checkpoint 产出逐字节相同的分片(推理服务确定性由 CPU 推理保证)。

### 8.3 本地推理服务(训练期)

- Python 进程,加载当前最佳 checkpoint,监听 localhost TCP;
- 协议:长度前缀帧 = JSON 头 + f16 批量特征;响应 = 批量策略 logits(8+31)与价值(4);
- 动态 batching:短暂窗口(默认 10ms)聚合多个自博弈进程的请求;
- 训练期**不做**每 checkpoint 的 CoreML 转换;CoreML 仅对竞技场晋级者导出(§9.3)。

## 9. 训练管线(tools/training/,Python)

### 9.1 数据与损失

- 数据:分片目录滑动窗口(保留最近 N 局,N 可配,默认覆盖最近 200k 样本),当前全部为 4 人局;滑窗用 `np.memmap` 磁盘映射,不全量驻留内存;
- **内存约束(8 GB M1,已确认)**:自博弈与训练**错峰串行执行**——自博弈期只跑推理服务与棋局进程(峰值 ~2 GB),训练期只跑训练进程(峰值 ~2 GB),禁止两阶段同时运行;
- 损失:`L = 交叉熵(策略A) + 交叉熵(策略B) + MSE(价值,人数 mask) + 10⁻⁴·L2`;
- 优化器:AdamW,lr 1e-3 起,余弦退火;批大小 1,024(Mac MPS 显存内);
- 每步训练指标:双策略准确率、价值 MSE、梯度范数。

### 9.2 竞技场门控

- 新 checkpoint(每 X 千步或每epoch评估)与现任最佳打评估局(自博弈 CLI 的 eval 模式,双方各执一半先手/后手与座位,默认 100 局);
- 总胜率(按局加权,并列半分)>55% 才晋级为"现任最佳",触发:推理服务热加载 + CoreML 导出;
- 门控配置与历史记录落盘(`tools/training/runs/<id>/`),可追溯每次晋级。

### 9.3 CoreML 导出

- `export.py`:torch checkpoint → coremltools → `.mlmodelc`(输入 multiArray Float32 [1,D],输出 policyAction[8]、policyCard[31]、value[4]);
- 导出产物带元数据:checkpoint id、featuresVersion、导出时间、布局哈希;
- App 校验 featuresVersion 与编码器一致才加载,不一致直接拒绝启动 AI(防旧模型配新编码)。

### 9.4 规模预期(诚实声明)

一台 Mac 上,V1 目标定位是"**稳胜随机与新手**":预计需要数千局自博弈(数小时到一两天训练)。接近人类高手需要数万至数十万局,是持续迭代的长期过程,不阻塞任何 App 阶段交付(端上启发式 MCTS 一直可用)。

## 10. App 接入

### 10.1 单机对 AI 模式

- 首页新入口「单人挑战」:固定 4 人局(1 名玩家 + 3 个 AI 座位)、AI 难度(轻量/标准/深思)、玩家颜色;
- 开局走现有本地会话管线(Loopback/本地 HostEngine),宿主=本机;座位 2..N 由 `AIPlayerDriver` 接管;
- 不出网、不进多人大厅;退出即销毁(不进持久化恢复流程,与现行 demo 对局一致)。

### 10.2 多人房 AI 补位

- 大厅界面:房主可将未就座的座位标记为 AI(选难度);**AI 补位当前限总席位数 = 4 的房间**(2/3 席总局暂缓,真人局不受影响);开始对局后,宿主侧 `AIPlayerDriver` 接管该座位;
- **协议零改动**:AI 的动作就是宿主以该座位身份提交的普通 `PlayerIntent`(座位自带 reconnectToken,机制现成);远端玩家只看到该座位正常出牌,显示名标注「AI·难度」;
- 房主中途断线恢复后 AI 配置随房间状态持久化重建。

### 10.3 AIPlayerDriver(宿主侧 actor)

- 职责:监听权威状态流 → AI 座位成为 `activePlayerID`(或进入其强卖阶段)时发起搜索 → 得到意图后提交;提交失败(如版本过期)则基于最新状态重搜,上限重试 3 次;
- 节奏:每步动作加最小展示延迟(默认 0.8s,可配置),避免机械连点;搜索用 `Task` 承载,人类撤回、对局结束、断线时立即取消;
- 结算与确认:时代结算阶段 AI 座位自动确认;终局自动停机;
- UI:AI 回合顶部指示条 + 思考动画(现有动效体系内);DEBUG 构建追加候选调试面板(top-5 动作、访问数、价值估计、单步耗时)。

### 10.4 模型资产管理

- App bundle 内置最近一次晋级的 CoreML 模型 + 元数据;启动时校验 `featuresVersion`;
- 模型加载失败 → 静默降级启发式评估,并在 AI 调试面板标注当前评估来源(coreml / heuristic)。

## 11. 分阶段交付与验收

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| **P0** 引擎底座 | `FastActionEnumerator`(完备+截断双模式)、`SimulationRunner`、无摘要快速路径、golden/对拍测试 | ① 随机状态集上完备枚举全量 submit 通过率 100%(≥10k 状态);② 模拟路径与宿主路径状态逐字段一致;③ 枚举吞吐满足:单决策完备枚举 ≤50ms(开发机) |

| **P2** 训练管线 | `StateEncoder` + golden、selfplay CLI、推理服务、训练脚本、竞技场门控 | ① 自博弈 4 人局 ≥100 局全程零规则拒绝;② 训练收敛(单批过拟合测试 + 价值 MSE 显著低于初始);③ 门控晋级流程完整走通一次 |

## 12. 测试策略

- **枚举正确性(P0 核心)**:完备枚举 → 全量 `HostEngine.submit` 接受;与 `ExactCompletionSearch` 交叉验证;边界:强卖中、结算中、终局、运河一轮(单动作回合)、万能牌堆耗尽。
- **路径等价**:随机动作序列下 `HostEngine` vs `SimulationRunner` 的 `GameState.canonicalHash` 一致(抽样)。
- **编码器 golden**:固定种子局 → 张量哈希;布局清单变更必须伴随版本递增的显式断言。
- **MCTS 单元**:合成小树上的 PUCT 选择、备份、温度采样数学正确性;多人并列排名效用正确。
- **驱动器**:AI 座位激活才出招、人类座位绝不动、撤回触发取消、重试上限、结算自动确认。
- **训练侧**:单批过拟合(两策略 acc→1、价值 MSE→0 方向)、旧 featuresVersion 数据被拒、门控晋级/否决分支。
- **端到端**:P1/P3 各自的全局对局冒烟(见阶段验收)。
- **回归**:自博弈与全量枚举本身是规则引擎的最强 fuzz——所有暴露的拒绝路径按引擎 bug 处理,修复需附最小复现测试(呼应已知测试债,顺手清偿)。

## 13. 风险与缓解

| 风险 | 等级 | 缓解 |
|---|---|---|
| 动作枚举/模拟性能不足以支撑模拟量级 | 高 | 无摘要快速路径;top-K 截断;P0 设吞吐验收线,不达标先优化(布局索引、去重结构)再进入 P1 |
| 单机训练算力不足,V1 棋力不及预期 | 中 | 目标定为稳胜新手;难度档位调节;启发式 AI 兜底常驻 |
| 多人局搜索质量下降(对手建模弱) | 中 | MaxN 备份为标准做法;价值向量含全部玩家;单一 4 人局形态训练,数据分布更集中 |
| 自博弈暴露规则引擎 bug | 中 | 视为收益:每个拒绝路径→最小复现→修复;P0 验收线本身就是压力测试 |
| CoreML/MPS 算子兼容问题 | 低 | 网络只用 MLP 级算子,无自定义层;导出脚本带数值对拍(PyTorch vs CoreML 输出容差断言) |
| 规则集后续演进(v2018.11 → 新版) | 低 | `featuresVersion` + 分片版本头隔离旧数据;引擎单源,升级一处生效 |

## 14. 假设与开放问题

**假设**:

- 训练与自博弈仅在作者本人的 Mac 上进行,无外部算力;
- v2018.11 规则集为当前唯一规则基线(与数据目录、RULES.md 一致);
- CoreML 模型随 App 打包,不做运行时下载。

**开放问题**(不阻塞 P0–P2,进入 P3 前决定):

1. V2 目标头(位置/路线级先验)的收益评估——待 V1 模型训练完成后用对局数据决策;
2. 完美信息 → 采样决定化的升级时机——待 V1 上手体验后评估必要性;
3. 轻量档是否引入"故意次优"(弱化搜索预算之外的人工失误)以改善新手体验;
4. 2/3 人局的开放时机——编码器与价值头已按 4 玩家向量设计,天然兼容更少人数;开放成本主要是补充对应人数的自博弈数据与再训练,不动任何结构。

## 15. 术语表

- **PUCT**:AlphaZero 使用的树搜索选择公式(Prior-biased UCT);
- **MaxN 备份**:多人博弈树中"轮到谁就最大化谁"的回传方式;
- **决定化(determinization)**:对隐藏信息采样出具体值再按完美信息搜索;
- **竞技场门控(arena gating)**:新模型必须击败现任最佳才上位的晋级机制;
- **渐进加宽(progressive widening)**:限制每节点展开子节点数以控制大分支因子,本文采用其 top-K 截断变体。
