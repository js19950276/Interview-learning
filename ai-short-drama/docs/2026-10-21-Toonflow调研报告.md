# Toonflow 开源项目调研报告

> 调研对象：[HBAI-Ltd/Toonflow-app](https://github.com/HBAI-Ltd/Toonflow-app)
> 数据截止：2026-10-21（GitHub API + 仓库 README + commit 记录 + TF-Router 子项目）
> 调研背景：本仓库（短剧钩子重构 Agent）处于同一赛道，需了解竞品/互补项目的定位、架构与打法。

---

## TL;DR

Toonflow 是目前 GitHub 上星数最高的 AI 短剧/漫剧创作工具（18.8k★，2026-01-29 建仓，约 9 个月登顶赛道）。它由北京爱阿科技有限公司开发，定位是**本地部署优先的无限画布式 AI 创作工作台**：剧本、角色资产、分镜、图片/视频生成整合在同一张节点画布上，模型全部外接（第三方 API / 本地 ComfyUI / 本地 LLM），自身不绑定任何模型。

对我们最关键的三点判断：

1. **它和我们不重叠，是上下游关系**。Toonflow 的剧本能力只有"文本节点 + LLM 辅助"，没有节奏规划、多变体、评分、合规、IP 风控这套深管线；而我们的产物（video_prompts.json / 分镜 xlsx / 剪映草稿）正是它画布需要的输入。
2. **它的分层工程值得抄**：供应商层（providers）、节点脚手架（nodeScaffold/nodeShared）、统一文件入口 + 原子写（writeAtomic）、媒体估价——与我们 state.json 分层、`.tmp + os.replace` 原子写、usage_by_stage 的思路互相印证。
3. **它的商业化路径有参考价值**：客户端完全 MIT 免费，靠自营模型中转平台 TF-Router（源码也开源）+ 赞助商 + 云平台付费镜像活下来；协议从 AGPL → Apache → MIT 三次放宽，用开放换生态。

## 2. 产品定位与核心能力

一句话：**把剧本、资产与视频片段整合进同一张无限画布的开源 AI 短剧工厂**（README 自述对标 LibTV / Tapnow 的 canvas-based 方案）。

核心能力（README 亮点表）：

- **本地部署**：桌面（Windows/macOS）、Android ARM64（内置本地 Bun 后端可独立运行，也可扫码"设备互联"连电脑或远程后端）、Docker、Linux 服务器四种形态。
- **无限画布**：文本节点（剧本/分镜/人物设定）、图片节点、视频节点、角色/场景/道具资产画布，同一画布组织。
- **节点式生成工作流**：内置 9 种节点——textNode、imageNode、videoNode、audioNode、imageGenerationNode、videoGenerationNode、audioGenerationNode、**director3dNode**（3D 导演台与镜头预演，与腾讯混元 3D 合作）、**frameAnalysisNode**（逐帧拉片）。
- **开放 Agent**：10 种内置工具（askUser、assetOperator、browser、canvas、ffmpeg、mediaGeneration、skillOperator、webFetch、webSearch、workspace），提示词、工具和 A2A 均开放，可自定义 Agent 行为。
- **MCP 接入** + **插件市场**（第三方可扩展节点、工具与创作能力）。
- **模型自由**：配置任意第三方 API，也接本地 ComfyUI 和本地 LLM；自营 TF-Router 中转平台兜底。
- 21 种界面语言；**媒体估价/余额同步**（花钱前先看到这一批要花多少）。

官方标准制作流程（四步，人工审阅贯穿）：

1. 文本节点写剧本与分镜（LLM 辅助 + 人工审改）；
2. 导入参考图或用图片生成节点做角色（含三视图）、场景、分镜图；
3. 连接文本与图片参考，选视频模型按镜头生成视频片段；
4. 画布预览、整理、下载，按需进入后期。

内置 skills 三个：`canvas`、`workflow`、`v118workflow`（v1.1.8 时代的分集制作流程 Skill，10 月仍在迭代）——把"制作方法论"做成产品内置技能，与我们把 HOOK_TYPE_GUIDES / BEAT_RULES 沉淀为 prompt 模块是同一打法。

## 3. 架构与工程实现

### 3.1 Monorepo 结构

```
apps/
  desktop/     # Electrobun 壳 + NSIS 安装器 + C# native helper（WebView2 检测/协议/更新）
  mobile/      # Android（GeckoView 备用内核）
  server/      # Bun + TypeScript + ESM + Express；createApp() 供桌面端复用
  updateServer/
  web/         # Vue 3 前端（Pinia + SCSS）
packages/
  nodes/           # 9 个内置节点（见上）
  tools/           # 10 个内置 Agent 工具
  skills/          # canvas / workflow / v118workflow
  providers/       # 供应商适配层（含自定义供应商接入 ComfyUI 工作流）
  ext/             # canvasNode / image / md / media / txt 文件扩展
  asr / ffmpeg / file / i18n / mcp / startup / modelIcons / assets
  nodeScaffold / nodeShared / toolScaffold / extScaffold / teamScaffold
  teams/
```

### 3.2 值得注意的工程决策（来自仓库内 AGENTS.md 开发规范）

- **统一文件操作入口**：全部磁盘操作走 `@toonflow/file`，禁止各模块直接调 `fs`/`Bun.write`；完整快照（JSON/画布/配置）必须 `writeAtomic` 原子写——与我们 state 持久化的 `.tmp + os.replace` 完全同思路，互相印证这是刚需。
- **插件边界铁律**：插件专属逻辑放插件内，跨插件共享放 `nodeShared`，脚手架只提供基础能力——三层边界（scaffold / shared / plugin）清晰。
- **命名全小驼峰**（文件/组件/属性/绑定一竿子到底）、`.vue` 顶层 template→script→style 顺序等，规范极细。
- 数据层升级到 **Drizzle ORM，本地/PostgreSQL/MySQL 可选**（第三次重构承诺，为二开降低门槛）。
- 服务端**无鉴权**（3000 端口），官方明确要求自托管用防火墙/SSH 隧道/带认证反代——自部署时要注意。

### 3.3 质量观

从 commit 与文档看，团队打法是"大颗粒 feature commit + 社区小修 PR"：主力开发 `ACT丶流星雨` 一天可推多个 feature 级提交，HBAI-Ltd 账号负责合并社区 PR（Clearlove275、wwmogu、miaobuao 等数人）。**bus factor 高**：核心代码高度集中在一人手中，这是单公司主导开源项目的典型风险。

## 5. 商业模式

| 收入线 | 说明 |
|---|---|
| TF-Router 官方中转 | 自营 API 网关（聚合 OpenAI/火山等），与火山签了 Seedance 年框，活动期"平进平出不赚差价"，之后收少量服务费；**平台源码开源**（86★，Node24+Express5+MySQL/Redis/RabbitMQ，供应商逻辑存库 + VM2 沙箱热更新、熔断降级、预付费计费） |
| 赞助商 | 秘塔（MiniMax H3 768P 0.09 元/秒）、APIMart（低价图像 API）、优云智算 CompShare（H3 0.08 元/秒）——全是模型渠道方，目标用户重合 |
| 云平台付费镜像 | 智星云官方授权商用镜像 |
| 其他 | 苹果签名赞助、算力赞助（Codex 20x）、潜在课程/广告位 |

公开信里对商业化纠结得很坦白（"不想让人觉得恰饭"），最终选择"客户端彻底免费开源 + 渠道抽佣"的组合，并把中转平台也开源以换取信任。**对独立开发者的启示：在模型渠道上做增值（聚合+计费+可靠性）比在工具本身收费更可持续。**

## 6. 制作成本基准（官方案例）

| 项 | 数据 |
|---|---|
| 制作周期 / 成片长度 | 约 2 小时 / 约 2 分钟 |
| 视频模型 | Seedance 2.0（约 ¥120） |
| 图片模型 | GPT Image 2（不足 ¥1） |
| 语言模型 | Claude Opus 4.6（约 ¥10） |
| 总成本 | 约 ¥130 |

这个数字对算账很有用：当前行情下**视频生成占成本 90%+**，剧本/文本层成本几乎可忽略——意味着我们这类"剧本层提质"工具的调用成本天花板极低，价值杠杆在"减少视频层的废镜头"（好的分镜 = 少生成废片）。

## 7. 优势与风险

**优势**
1. 赛道第一的心智 + 双国产平台认证（Gitee GVP / AtomGit G-Star），21 语言全球化布局；
2. 本地部署 + 模型自由 + MIT，踩中创作者对数据与成本的核心焦虑；
3. 工程分层成熟（providers/nodes/tools/skills/ext + 四套脚手架），插件市场形成生态位；
4. 迭代速度极快（周更）且能自我革命（三次重构、换协议）。

**风险 / 局限**
1. **剧本深度弱**：无节奏规划、多变体对比、确定性质量门、三视角评分、合规/IP 风控——它解决"生成与组织"，不解决"哪个版本更能爆"；
2. 核心开发集中一人，社区贡献以小修为主，长期维护存在 bus factor 风险；
3. 服务端无鉴权，企业自托管需自行加固；
4. 商业化依赖中转平台（本质是渠道生意），若上游厂商直营化或价格战，利润空间受挤压；
5. 295MB 仓库体积、issues 收敛到反馈表，社区治理偏"运营驱动"而非"开源治理驱动"。

## 8. 对本项目（短剧钩子重构 Agent）的启示

1. **定位错位 = 机会**：我们是"剧本→提示词"的深管线，Toonflow 是"提示词→成片"的画布。我们输出的 video_prompts.json（Seedance/H3 方言）与分镜素材理论上可以直接喂进它的文本/视频节点。**可选动作：把我们的管线包成 MCP server**——Toonflow 明确支持 MCP 接入，意味着"钩子重构 + 评分 + 合规"可以成为它生态里的一个外部工具，这是最低成本的生态借力。
2. **借鉴供应商层抽象**：它把"模型差异"全部收敛到 providers 层（含自定义供应商接 ComfyUI）。我们目前只有 llm-proxy 单一文本接口；未来若接图像/视频模型做预览生成，先设计 provider 抽象再接第一家。
3. **借鉴"先估价再花钱"**：它的媒体估价/余额同步把成本前移到点击之前。我们有 usage_by_stage 事后统计，可以加一层"跑这个剧本预计花多少"的 preflight 估算（文本层极便宜，重点在提示词分发给视频层后的预期视频成本估算）。
4. **writeAtomic / 文件入口统一**：与我们现有做法互证，无需改动；若未来插件化，可参考它的 scaffold/shared/plugin 三层边界。
5. **方法论即 Skill**：它把制作流程做成内置 v118workflow skill 的做法，提示我们可以把"钩子重构管线"剥离出 Streamlit，同时发布为可被 Claude Code/Codex 装的 Agent Skill（参照 zenstory/drama-skills 3.2k★ 的热度，skill 分发是被验证过的渠道）。
6. **成本论据**：视频生成占制作成本 90%+，我们的质量门/评分如果能把废镜头率降 20%，对用户的价值远超文本层 API 费用——这是对外讲故事时的核心话术。
